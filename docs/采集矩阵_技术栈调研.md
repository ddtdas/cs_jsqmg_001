# 采集矩阵 — GitHub 技术栈调研（2026-09-16 实测）

> 调研目的：为『采集矩阵』功能（多平台账号 × 采集策略的采集编排矩阵）从 GitHub 寻找合适技术栈，并以**嵌入集成**方式融入项目（非独立部署）。
> 数据来源：2026-09-16 通过 GitHub API 实测各仓库 star 数（约数，会随时间变化）；仓库用途与嵌入方式结合本项目架构（FastAPI 主控 + 账号桥 + APScheduler）评估。
> 总原则：**参考实现 + 桥适配器 + 文档**，绝不把重型独立服务（如 Scrapy 调度器、独立浏览器服务）跑进主控进程。

## 二、分项调研详情

### 1. Scrapy
- **仓库**：https://github.com/scrapy/scrapy
- **★**：约 64k
- **用途**：通用爬虫框架，提供请求调度、中间件、去重（RequestFingerprinter）、Item 管道等完整爬虫生命周期能力，生态成熟。
- **嵌入方式**：本项目只需其**去重与调度思想**——URL 指纹去重（md5(url) 集合）+ 请求队列 + 重试；不引入 Scrapy 本身（与 FastAPI 同进程过重，且其 Twisted 事件循环与 asyncio 混跑有风险）。
- **来源链接**：https://github.com/scrapy/scrapy

### 2. Crawlee for Python
- **仓库**：https://github.com/apify/crawlee
- **★**：约 1.1k
- **用途**：Apify 出品的通用网页采集框架（Python 版），支持 playwright/httpx 两种运行器，内置自动重试、代理轮换、请求去重、结果去重。
- **嵌入方式**：作为 `collector` 引擎的**参考实现**——若 `pip install crawlee` 可通则直接作为可选依赖引入；若网络受限则按同模式自实现（httpx 客户端 + 指数退避重试 + 指纹去重 + 令牌桶限速），全部复用项目既有 zhihu_bridge 基建。
- **来源链接**：https://github.com/apify/crawlee

### 3. DecryptLogin
- **仓库**：https://github.com/CharlesPikachu/DecryptLogin
- **★**：约 2.8k
- **用途**：知乎/微博/QQ 等多平台**登录态解密**库（RSA 加密参数、签名算法逆向）。
- **嵌入方式**：仅借鉴其**签名算法思路**（如知乎 x-zse-96 的构造方式）用于自有 httpx 通道；**不引入第三方凭据处理**（合规红线：凭据仍走项目 Fernet 加密存储与账号桥）。
- **来源链接**：https://github.com/CharlesPikachu/DecryptLogin

## 三、嵌入集成原则（确保是"嵌入"而非"独立部署"）

1. **模块即项目一部分**：`app/services/collector.py` + `app/api/collector.py` + `app/models/__init__.py` 迁移（collector_matrix 表）——与既有 FastAPI 同进程，无独立服务、无额外端口。
2. **复用既有基建，不重复造**：令牌桶限速 / 指数退避 / Fernet 凭据加密 / 近重复判定（INGEST_NEAR_DUP_THRESHOLD）/ events / gate_logs 全部复用。
3. **开源技术栈 = 参考实现 + 桥适配器 + 文档**：
   - Crawlee 模式：`pip install crawlee` 可通则用，否则同模式自实现；
   - DecryptLogin / zhihu_spider：仅借鉴签名思路（合规：不引入第三方凭据处理）；
   - WeChatFerry / NapCatQQ / python-telegram-bot：以**桥适配器**集成（账号桥已列 wechat/qq/telegram），主控只做 HTTP/webhook 对接与状态登记。
4. **调度嵌入**：挂 APScheduler 既有 scheduler.py（复用既有 job 模式），新增 `job_collector_matrix` 按 enabled 单元格轮询执行（frequency 节流），防御式（异常落 error 不崩）。

## 四、采集矩阵设计摘要

### 4.1 概念
采集矩阵 = **平台 × 账号 × 采集策略** 的编排表（collector_matrix 表）。
- 平台：zhihu / weibo / telegram / wechat(桥) / qq(桥) / rsshub(公开聚合)
- 账号：来自 account_bridges 配置的已配置账号（rsshub 无账号）
- 策略：采集类型（dm/comments/posts/follows）、频率（minute/hourly/daily）、深度、关键词过滤、近重复阈值（复用 ingest_near_dup）
- 状态：pending/running/ok/error + last_run_at + last_item_id

### 4.2 表结构（幂等迁移）
```sql
CREATE TABLE IF NOT EXISTS collector_matrix (
  id INTEGER PRIMARY KEY,
  platform TEXT NOT NULL,
  account TEXT DEFAULT '',
  strategy TEXT NOT NULL,          -- JSON: {collect, frequency, depth, keyword, near_dup}
  enabled INTEGER DEFAULT 1,
  status TEXT DEFAULT 'pending',   -- pending|running|ok|error
  last_run_at TEXT, last_item_id TEXT, last_error TEXT, note TEXT,
  created_at TEXT, updated_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_collector_matrix_platform ON collector_matrix(platform);
```

### 4.3 后端
- `CollectorService`：list_matrix / add_cell / update_cell / remove_cell / run_cell / run_all；
- 采集执行（Crawlee 式）：`_fetch`（httpx + 指数退避 + 令牌桶）、`_dedupe`（近重复判定）、`_ingest`（复用 ingest 逻辑，写 events(kind='collector_run')）；
- 平台适配器：知乎（CH-A/CH-B/降级 CH-C）、微博、Telegram（getUpdates）、RSSHub（公开聚合）、微信/QQ（桥登记）；
- 调度：APScheduler `job_collector_matrix`（防御式）。

### 4.4 API（前缀 /api/v1/collector）
| 端点 | 方法 | 说明 |
|---|---|---|
| /matrix | GET | 矩阵全表 |
| /matrix | POST | 新增单元格 |
| /matrix/{id} | PUT | 更新策略/启停 |
| /matrix/{id} | DELETE | 删除单元格 |
| /matrix/{id}/run | POST | 立即执行单格 |
| /matrix/run-all | POST | 执行所有 enabled 格（限速节流） |
| /tech-stack | GET | 本文档技术栈结论（静态元数据，前端"爬虫技术栈"页用） |

### 4.5 前端
`webui/src/views/CollectorMatrixView.vue` + 路由 `/collector-matrix` + 侧边栏菜单"采集矩阵"：
矩阵表格（平台/账号/策略/状态/最近运行/操作）、新增弹窗（平台/账号/策略表单）、"爬虫技术栈"卡片区（展示 /tech-stack：Scrapy/Crawlee/DecryptLogin/Wechaty/WeChatFerry/zhihu_spider/NapCat/python-telegram-bot + ★ + 集成说明，可展开文档链接）。

### 4.6 合规（不变）
只读自有/公开信息；不自动发布；凭据加密（Fernet）；限速；HITL；采集内容进检测流水线（ingest → 检测 → 反向侦察）而非直接外发。
