# 第 1 轮 M · 复杂化验收计划（跨模块集成与端到端新形态）

> 项目：金丝雀蜜罐 CanaryGuard AntiFraud v1.0.0
> 计划作者：acceptance-planner（验收规划与指导工程师）
> 基线：前三轮 120 用例全绿（功能深挖→安全对抗→真实场景）+ 企业级审查 8.0/10 + pytest 240 passed / e2e 63/63
> 本轮方向：**跨模块集成与端到端新形态** —— 模块间数据流一致性、多客户端协同、多实例/多进程边界、引擎联动与降级链、WebUI 契约级联、配置联动
> 计划规模：**37 条用例**（P0×15 / P1×18 / P2×4；P0+P1 占比 89.2% ≥ 60%）
> 预期耗时：≈5.5h（可按 §7 压缩路径收敛至 ≈5h）

---

## 1. 方向定位与差异化声明（与前几轮明确不同）

| 轮次 | 方向 | 视角 | 本轮不重复 |
|---|---|---|---|
| 第 1 轮 | 功能全流程深挖 + 边界/回归 | 单模块内"功能是否对" | 单端点正确性、状态机矩阵、认证/限流基础行为 |
| 第 2 轮 | 安全对抗与工程化纵深 | 单模块/单端点"能否被攻破" | 脱敏字形绕过、注入、int64、config 键名白名单等对抗项 |
| 第 3 轮 | 真实场景/并发压力/故障注入 | 单实例内"扛不扛得住" | 单进程并发跑批、强杀恢复、长稳、规模压测 |
| **本轮（M）** | **跨模块集成与端到端新形态** | **"模块之间怎么协同、多客户端怎么打通、边界交互与降级联动"** | 只验证**跨模块/跨客户端/跨进程/跨配置**的联动一致性，不重跑任何单模块功能用例 |

差异化原则：
1. **数据以"一条威胁文本的完整旅程"为对象**（导入→扫描→分级→告警→证据→案例→图谱→事件→会话），而不是单端点返回。
2. **客户端以三端并发为对象**（WebUI + MCP + curl 同一主控），而不是单客户端挂载可用。
3. **进程以"≥2 实例 / workers>1"为对象**，突破前几轮"单进程单库"隐含假设。
4. **降级以"引擎间联动链"为对象**（LLM 故障同时影响 speech/trap/desensitize 三引擎），而不是单引擎降级。
5. **契约以"前端每调用 vs openapi 每端点"逐条核对**，而不是单个页面功能。
6. **配置以"一次热更新多模块同时生效 + reset-key 三端同时失效"为对象**。

关键实现事实（计划依据，qa-tester 执行时可复核）：
- 同一内核（D1）：WebUI/MCP/curl 都是 `http://127.0.0.1:9200/api/v1` REST 的客户端；MCP 为 httpx 纯透传（36 工具），统一封包 `{ok:true,data} | {ok:false,error:{code,message}}`。
- 数据流：`POST /zhihu/import`（CH-D）→ `detections(status=pending)` → `POST /scan/inbox` 或 `POST /scan/text`（SpeechEngine 规则→LLM→judge）→ `GradingService.finalize`（L1–L5 + `grade_reason`）→ `AlertService.evaluate`（仅 L3+ 写 alerts）→ `POST /evidence/build`（哈希链）→ `POST /cases/publish`（脱敏 + confirm+reason + GateLog）→ `GET /cases/graph` → `events` 表全程 9+ 类事件。
- 状态机：蜜饵 `draft→active→monitored→hit→retired`；hit 即退役；禁用（enabled=0）后不可 check-hit。
- 调度器 6 job：job_scan_dm / job_zhihu_sync / job_trap_recheck / job_account_scan / job_evidence / job_case_publish（全程 HITL：job_case_publish 只产 `case_ready` 事件，绝不自动发布）。
- 降级链：LLM 熔断（连续失败≥3 → open → 冷却 60s → half-open 单飞探活 → close）；`rule_min_llm` 可热更新；蜜饵生成 LLM 不可用→模板池；告警报文与图谱不依赖 LLM。
- 配置热更新键白名单（8 个）：`grading.l3_min / speech.rule_min_llm / trap.simhash_threshold / trap.overlap_threshold / llm.max_fail_streak / llm.daily_budget / llm.cooldown_seconds / zhihu.ingest_near_dup_threshold`。
- 进程内锁：`_PUBLISH_LOCK`（cases）、`_RESET_LOCK`（auth）——**仅进程内有效**，跨进程/多 worker 是边界风险点。
- 已知 P2 观察（跨模块相关，本轮顺带复验）：同 det 重复发布 200 无提示；job_evidence 去重用 `det_ids LIKE '%{id}%'` 子串匹配（单/多位数 ID 可能误判）；alert 去重用 `payload LIKE '%"detection_id": N%'` 文本匹配。

## 4. 详细用例

### 类别 A：跨模块数据流一致性（8 条）

#### A1【P0】全链路 ID 追踪：一条威胁文本从导入到案例的同一 detection_id
- **前置**：主控运行；admin key；全新威胁文本 `qa_m_A1_<ts>`（>20 字、含高权重话术词，如"稳赚不赔 加导师微信 垫付保证金 先转账后返利 内部渠道"，确保 rule_score≥10 → L3+）。
- **操作**：
  1. `POST /api/v1/zhihu/import`（source=zhihu, from_url_name=qa_m_zhang）→ 记录返回 `detection_id=D`（duplicate=false）；
  2. `POST /api/v1/scan/inbox` → 处理 1 条；
  3. `GET /api/v1/grading/explain/{D}` → 记录 grade；
  4. `GET /api/v1/alerts` → 找到 payload.detection_id==D 的告警；
  5. `POST /api/v1/evidence/build` body `{"det_ids":[D]}` → pkg_id；
  6. `POST /api/v1/cases/publish`（redacted 全文脱敏后文本，confirm=true, reason≥20）→ case_id；
  7. `GET /api/v1/events?page_size=100` → 过滤 payload 含 D 的事件。
- **预期**：1 步返回同一 D 且 duplicate=false；2 步 processed 含 D；3 步 explain 返回 D；4 步告警 payload.detection_id == D；5 步 det_ids == [D]；6 步 case.det_id == D；7 步存在 `detection_scanned` / `detection_graded` / `alert_created` / `evidence_built` / `case_published` 且各自 payload 中 ID 与 D 严格一致。
- **判定标准**：全链 7 个模块引用的 detection_id 全部等于 D；事件流 5 类事件齐备；任一不一致即 FAIL（P0）。
- **差异化**：前轮 A1/A10 只验证单链存在，本轮验证**跨 7 模块的同一主键贯通**。

#### A2【P0】同一 detection 跨端点字段一致性
- **前置**：A1 产生的 detection D 及其 evidence pkg、case。
- **操作**：在同一时间窗口内依次读取 4 个来源并比对字段：`GET /scan/hits`（D 行）、`GET /grading/explain/{D}`、`GET /evidence/{pkg}`（导出 items 中 D）、`GET /cases`（该 case 的 graph_tags / redacted_payload）。
- **预期**：rule_score、judge_confidence、grade 四源一致；case.graph_tags 与 publish 提交值或 `_derive_tags` 推倒值一致；desensitize_log 与提交一致。
- **判定标准**：字段值四源完全一致（时间窗口内无并发写的前提下）；任何不一致 → FAIL P0。
- **差异化**：前轮"逐端点正确"升级为"**跨端点的同一实体视图一致性**"。

#### A3【P0】状态流转时序一致性（pending→scanned→graded→alert→case）
- **前置**：导入 2 条文本（一条 L1 正常文本、一条 L5 高命中文）。
- **操作**：
  1. import → 立刻 `GET /scan/inbox`（读）确认 status=pending、grade 为空；
  2. scan/inbox 消费 → status=scanned、grade 非空；
  3. `GET /alerts`：L1 文本无告警，高命中文本有告警（L3+）；
  4. 对 L1 文本（grade=L1）尝试 `POST /cases/publish`（confirm+reason 合规）；
  5. 对高命中文的 detection 重复 publish 两次（同 det）。
- **预期**：3 步满足 L3+ 告警闸控；4 步——按实现口径 publish 只校验 det 存在（404 保护），**允许未分级/低分级发布**（记录行为，图谱按 L1 兜底）；5 步——两次均 200 无提示（延续 P2-1 观察，本轮留档）。
- **判定标准**：状态机顺序（pending→scanned→graded）不被破坏；告警闸控只对 L3+ 生成；任何"未扫描即有 grade/告警"现象即 FAIL P0；4/5 步按"契约 vs 实现"记录（是否需修复由复验定级）。
- **差异化**：前轮 C 类验证蜜饵状态机；本轮验证**检测/告警/案例三级业务状态在同一实体上的时序约束**。

#### A4【P1】引用完整性：reset-key / retire / 冻结后无孤儿、审计链完整
- **前置**：当前 key 快照；新建 1 个蜜饵并 deploy→monitor，制造 1 个证据包并 freeze。
- **操作**：
  1. `POST /auth/reset-key`（confirm+reason）→ 立即 `GET /system/audit-verify`；直连库查 `api_keys`（enabled=1 行数、明文 key 是否落库）；
  2. retire 该蜜饵（confirm+reason）→ `GET /system/audit-verify` 仍 valid；`speech_hits` 不引用蜜饵（无外键语义，检查事件链无半残）；
  3. freeze 后篡改证据包内容（直接改库 content）→ `GET /evidence/{pkg}` verified.intact=false。
- **预期**：reset 后 enabled=1 恰 1 行 bootstrap、gate_logs 前后链完整（audit-verify 200 valid）；retire 后 audit-verify 仍 valid；篡改后 intact=false。
- **判定标准**：三处引用完整性全部成立；`audit_chain_broken` 出现即 FAIL P1。
- **差异化**：前轮 C5/C6 验证"链能否检出篡改"，本轮验证**状态操作后关联表无孤儿 + 审计链在敏感操作叠加下持续完整**。

#### A5【P1】事件流与业务动作一一对应（kind 全覆盖）
- **前置**：新建空事件基线（记录当前 events 最大 id）。
- **操作**：依次执行 10 个业务动作：生成蜜饵草稿 → deploy → monitor → check-hit 命中 → 扫描文本 → 分级（含 L3+ 告警）→ 已读告警 → build evidence → freeze evidence → publish case → 热更新 config → reset-key；每步后 `GET /events?kind=<期望kind>` 验证。
- **预期**：对应 kind 存在且 payload 含关键 ID：`trap_draft_created / trap_deployed / trap_monitored / trap_hit / trap_retired / detection_scanned / detection_graded / alert_created / alert_read / evidence_built / evidence_frozen / case_published / config_updated / admin_key_reset`；无动作丢事件、无多余 kind 误报。
- **判定标准**：≥11 类 kind 全部出现且 ID 关联正确；缺失任一 → FAIL P1（事件流是 WebUI/审计的跨模块消费源）。
- **差异化**：前轮 F6 只回归 detection_scanned 一类；本轮**全 kind 矩阵**。

#### A6【P1】accounts↔traps↔grading 跨模块关联
- **前置**：新建蜜饵并 deploy→monitor。
- **操作**：
  1. `POST /accounts/check` `{url_name: qa_m_a6, signals: {trap_hit_ids: [<monitored trap id>]}}` → risk_level；
  2. `POST /traps/{id}/check-hit` 命中 → 再 `POST /accounts/check` 同 url_name（trap_hit_ids 增补）→ risk 及证据链；
  3. `GET /accounts/{url_name}` 与 `GET /accounts/{account_id}/timeline` 验证 trap_hit 记录；
  4. `GET /grading/explain/{D}?trap_hit_count=1` 验证 L5。
- **预期**：带 trap_hit 的账号 risk=red 且证据链含 trap_hit_evidence；timeline 含 kind=trap_hit 条目；explain 带实锤 → L5。
- **判定标准**：四级联动（trap→account→evidence→grade）一致；任一断链 FAIL P1。
- **差异化**：前轮 A9 单链验证"账号速查→踩饵→画像"；本轮**把账号的 trap_hit_ids 注入分级并验证可解释链跨表闭环**。

#### A7【P1】调度器↔证据：job_evidence 幂等去重 LIKE 子串误判探测
- **前置**：直接改库构造证据包 `evidence_packages(det_ids="[12]")`（用 api 无法造出，直连库造即可），再构造 detection id=1（或 10–19 与包内 id 构成子串关系的单/多位数组合）。
- **操作**：独立 Python 子进程调用 `from app.services.scheduler import job_evidence; job_evidence()`（不等待 12h 定时器）→ 检查 id=1 的 L4/L5 检测是否被跳过构建。
- **预期**：实现缺陷暴露点——`det_ids LIKE '%1%'` 会命中 "[12]" 而误判"已构建"；单/多位数组合矩阵（包=[12] vs det=1/2/12/3）逐一记录 skip 行为。
- **判定标准**：det_id=12 应跳（真重复）、det_id=1 不应跳（假重复）；**假跳过 = FAIL P1**（跨模块引用一致性缺陷）；如实现无此缺陷则 PASS（记录"字符串匹配未误判"）。
- **差异化**：前轮只验证 job 不崩（X8），本轮**验证 job 决策与证据表的引用级正确性**。

#### A8【P2】告警去重 LIKE 文本匹配脆弱性（观察项）
- **前置**：构造一条 grade_reason/命中明细中含 `"detection_id": N` 字面文本的检测（如话术命中文本恰含该 JSON 字形）。
- **操作**：`AlertService.evaluate` 同 detection 二次评估（模拟重复扫描/重复 finalize）。
- **预期**：去重按 `payload LIKE '%"detection_id": N%'` 文本匹配——正常 JSON 序列化下可去重；含该字面的内容可能误判。记录行为，不阻断。
- **判定标准**：P2 观察；若发现可稳定误去重（合法重复告警被吞）则升级 P1。
- **差异化**：前轮 C8 验证 read 幂等；本轮观察**告警去重算法与 payload 内容的耦合风险**。

### 类别 B：多客户端协同（7 条）

#### B1【P0】三端读写同一资源最终一致
- **前置**：curl/httpx 会话、MCP stdio server（AF_API_KEY=当前 key）、浏览器 WebUI 已登录。
- **操作**：
  1. curl `POST /traps`（自拟文案）→ trap_id=T；
  2. 浏览器 WebUI 蜜饵页刷新/轮询到 T（状态 draft）；
  3. MCP `af_get_trap(T)` → 状态 draft；
  4. MCP `af_mark_trap_deployed(T)` → active；
  5. curl `GET /traps/{T}` → active；浏览器再刷新 → active；MCP 再查 → active。
- **预期**：三端对同一 T 的状态在每一步后**最终一致**（允许 ≤5s 轮询延迟）；任意顺序执行后状态机仍合法。
- **判定标准**：4 步内三端状态与后端一致；任何一端读到过期状态超过 5s 或与后端冲突 → FAIL P0。
- **差异化**：R1-A2/MCP 单链验证；**三端并发读写同一实体**为全新形态。

#### B2【P0】MCP 36 工具逐个真实穿透真实主控（含参数组合与错误路径）
- **前置**：真实主控 + 真实 admin key + MCP stdio；按 `mcp/server.py` 清单逐一校验工具存在。
- **操作**：对全部 36 工具逐个调用（真实穿透，非 mock）：
  1. readonly 组（15）：af_health、af_stats、af_list_traps(status)、af_get_trap、af_list_scan_hits(limit)、af_account_get、af_grading_levels、af_grade_explain(带 trap_hit_count/account_risk 组合)、af_get_evidence、af_export_evidence(fmt=json|text)、af_report_template(kind=96110|platform|pibyao)、af_list_cases(page/page_size/tag 组合)、af_case_graph、af_list_events(kind/page)、af_get_event、af_list_alerts(level/unread_only)、af_zhihu_channels、af_zhihu_status、af_config；
  2. 写组（11）：af_generate_trap_draft(template_id 组合)、af_mark_trap_deployed、af_disable_trap、af_scan_text(source 三值)、af_scan_inbox、af_account_check(signals 组合)、af_build_evidence(单 det/多 det + screenshots)、af_freeze_evidence、af_zhihu_login(ch-a 假 cookie → 期望 422 或 200 结构校验)、af_zhihu_verify、af_zhihu_import(text/JSON 两种)；
  3. 敏感组（5）：af_retire_trap 缺 confirm / confirm+短 reason / 合规；af_publish_case 缺 confirm / 合规（脱敏载荷）；af_config_update 白名单键 / 非白名单键 422 / 缺 confirm 403；
  4. 自描述（1）：af_register_agent。
- **预期**：36 工具全部可调用；REST 4xx 经 ProxyError 透传（isError=true 且消息含 `[code]`）；列表返回被 `{"items":[...]}` 包装；写组副作用在库中可查。
- **判定标准**：36/36 可通；≥30 个返回结构符合统一封包解包；错误路径 ≥8 个全部 code 可见；覆盖率 100% 为通过线（任何工具不可调或挂死 = FAIL P0）。
- **差异化**：R1-A7/A8 只测 2 条链路；**36 工具全量真实穿透**为本轮核心新维度。
- **耗时控制**：脚本化批量调用，约 45min（见 §7）。

#### B3【P0】MCP 错误码与 REST 等价透传
- **操作**：同一组违规操作分别走 REST 与 MCP，比对错误码：① af_retire_trap(confirm=false) vs curl POST retire（expect 403 `confirm_required`）；② reason=短文本 → 422 `reason_too_short`；③ af_publish_case 未脱敏载荷（含 11 位手机号）→ 422 `sensitive_content`（对齐 desensitize 拒绝）；④ af_get_evidence(999999) → 404 `evidence_not_found`。
- **预期**：MCP isError 消息含与 REST 完全相同的 code/message（R1-A8 修复的全面回归）。
- **判定标准**：8 组（4 场景 × 2 端）code 逐一相同；任何吞码 → FAIL P0。

#### B4【P1】WebUI 多标签页会话隔离与共享

- **预期**：会话按浏览器 session 存储介质语义隔离/共享；状态机冲突不产生 500。
- **判定标准**：①②符合 sessionStorage per-tab/复制语义；③冲突 4xx 且 UI 不白屏；任何 500 → FAIL P1。

#### B5【P1】WebUI↔MCP↔curl 同库读写互相可见
- **操作**：① MCP af_zhihu_import 导入文本 → 浏览器 ScanView/事件页可见该 detection（轮询）；② curl publish case → MCP af_list_cases 可见 + WebUI 案例库可见；③ WebUI 生成蜜饵 → MCP af_list_traps 可见。

- **判定标准**：3 组双向可见全部成立（≤5s）；任何一端看不到另一端的写 → FAIL P1。

#### B6【P1】三客户端并发 check-hit 同一蜜饵
- **前置**：新建蜜饵 deploy→monitor。
- **操作**：curl / MCP af_check_trap_hit / 浏览器（页面触发）三线程同时提交同一命中文本。
- **预期**：恰 1 个 200 hit=true；其余 409 `trap_retired`（已退役）或 `trap_disabled`；hit_count=1；events 中 trap_hit 恰 1 条（第 2 轮 P1-11 修复的**跨客户端**回归）。
- **判定标准**：200 恰 1、409 ≥1、hit_count=1、trap_hit 事件恰 1；任何重复命中/重复计数 → FAIL P1。

#### B7【P1】三端 401/429/404 封包结构一致性
- **操作**：① 无 key / 假 key 访问 `GET /system/stats`（REST 401、MCP af_stats isError [unauthorized]）；② 无 key 连打 `/scan/text` 61 次 → 429 `rate_limited`（REST 与 MCP af_scan_text 各触发）；③ 访问不存在资源 `/traps/99999999` → 404 `trap_not_found`（REST 与 MCP af_get_trap）。
- **预期**：三端错误码与封包结构（`{ok:false,error:{code,message}}`）完全一致。
- **判定标准**：9 组比对（3 场景 × 3 端）code/message 一致；不一致 FAIL P1。

### 类别 C：多实例/多进程边界（6 条）

#### C1【P0】双实例不同数据目录完全隔离
- **前置**：现有主控 9200（data/）；准备临时数据目录 `var/qa_roundM/inst_b`。
- **操作**：`AF_DATA_DIR=var/qa_roundM/inst_b AF_PORT=9202 python -m app.run`（后台）→ 实例 B 建库（ensure_schema）→ 在 9200 建蜜饵 T → 9202 `GET /traps` 无 T（隔离）；9202 建蜜饵 T2 → 9200 无 T2；两实例 health 均 OK；两实例 bootstrap key 文件独立。
- **预期**：数据完全隔离、互不干扰、各自自举建库。
- **判定标准**：双向不可见 + 双实例均 200 + key 文件不同；串库（一方数据可见于另一方）→ FAIL P0。
- **注意**：测试后 kill 9202 实例并清理临时目录。

#### C2【P0】同库双进程并发写（WAL/busy_timeout/零损坏）
- **前置**：用**同一 data 目录**启动实例 B（端口 9202，共享 af.db；注意 scheduler 双注册属预期观察，见 C4）。

- **预期**：busy_timeout=5s + publish 重试兜底 → 零 5xx（503 db_busy 可接受且随后重试成功）；WAL 下读不阻塞；库 integrity ok。
- **判定标准**：无 500、无误 404（InterfaceError 误报）、integrity=ok、行数与响应一致；违规即 FAIL P0。
- **差异化**：第 3 轮 X5/X6 是**单进程**注入故障；本轮是**双进程真并发共享一库**。

#### C3【P1】跨进程 reset-key 竞态（进程内锁局限暴露）
- **前置**：同库双实例运行中（接 C2）。
- **操作**：实例 A 与实例 B 各发起 reset-key（并发，均 confirm+reason 合规）→ 结束后检查 `api_keys`（enabled=1 行数）、key 文件内容、audit-verify。
- **预期**：进程内 `_RESET_LOCK` 只护单进程 → 跨进程并发会暴露文件写 vs 表更新的非原子性：记录 enabled 行数/文件 key 与最终生效 key 的关系。
- **判定标准**：若 enabled>1 或文件 key 与 api_keys 单行哈希不一致 → FAIL P1（多进程部署需文件锁/串行化，交 backend 修复）；无双活可用的 key 不判 P0（与第 2 轮口径一致）。测试后还原 key。

#### C4【P1】uvicorn workers=2：调度器双注册 / 熔断分片 / 锁失效观察
- **操作**：`python -m uvicorn app.main:app --port 9203 --workers 2`（独立端口+独立数据目录或临时库）→ 观察：① `日志中调度器已启动 job 数`出现 2 次（每 worker 各自 6 job → job 双执行风险）；② LLM 故障注入一侧 worker（熔断单例按进程分片）→ health/scan 由另一 worker 处理的行为；③ 并发 publish 20 次（两 worker 负载均衡）→ 进程内 `_PUBLISH_LOCK` 失效下 SQLite busy_timeout 是否仍兜底。
- **预期**：无数据损坏；记录并给多 worker 部署建议（scheduler 应仅 1 worker 启、进程内锁需进程外化）。
- **判定标准**：①若 job 被双执行且写入重复/幂等被破坏 → P1 记 backend；②锁失效不产生 500 → 可记录为部署约束 P2/P1；③有数据损坏 → FAIL P1。测试后清理 9203 实例与临时库。

#### C5【P1】重启时未完成操作一致性
- **前置**：主控 9200 运行；准备两笔未完成操作。
- **操作**：① import 2 条文本后**不消费**（保持 pending）；② 触发 build evidence 的同时强杀主控（`taskkill /F`，模拟构建中断）；重启主控 → 检查：pending 检测行保留且可被 scan/inbox 正常消费；无半写入的 evidence_packages（WAL 回滚）；`integrity_check` ok；stats 计数自洽。
- **预期**：第 3 轮 X6（杀在扫描中）扩展到"证据构建中/导入后未消费"两个中断点；重启后数据不丢不残。
- **判定标准**：pending 保留并消费成功、无半写行、integrity ok；违规 FAIL P1。

#### C6【P2】双进程写读下 WAL checkpoint 有界
- **操作**：C2 场景中同时启动读压力（持续 GET /cases、/events），记录 `af.db-wal` 大小峰值与 checkpoint 回落。
- **预期**：WAL 有界（参照第 3 轮单进程 4.2MB 量级，双进程允许适度上浮，观察记录）。

  1. 401：登录后用旧 key 刷新（F1 场景配合）→ 自动清凭据跳登录（onUnauthorized）；
  2. 422：扫描页提交超长/空文本（如 >20000 字）→ 友好提示（validation_error 转译文案），页面不展示 pydantic 原文；
  3. 403/404：深链到不存在蜜饵详情 → 页面不白屏、有错误提示；
  4. 429：页面 console 以无 key fetch 直呼 `/scan/text` 61 次 → 页面主体不崩（若 UI 正常路径因 admin 豁免不可达，则该路径经 console 模拟验证）。
- **预期**：每个错误码都有非崩溃、可理解的 UI 路径。
- **判定标准**：4 类错误码页面全部存活（无 JS 异常、无原始堆栈渲染）+ 跳转/提示正确；任何白屏/堆栈展示 → FAIL P0。

#### E3【P1】分页契约（page_size≤100 上限回归）
- **操作**：浏览器事件页（SessionsView）加载（历史 bug：pageSize=200）；pagesize 超限时页面表现；curl 侧 `?page_size=101` → 422 validation_error。
- **预期**：前端所有列表调用 page_size≤100（A10 修复回归）；超限请求被友好处理。
- **判定标准**：前端无超限调用 + 超限 422 文案友好；复发即 FAIL P1。

#### E4【P1】字段命名契约（snake_case 映射抽查 8 视图）
- **操作**：抽查 8 个视图（TrapsView / ScanView / EvidenceView / CasesView / AlertsView / EventsView / ZhihuView / SettingsView）中绑定响应字段名，与对应 API 返回字段逐一比对（如 `trap_hit_ids`、`redacted_payload`、`graph_tags`、`unread`、`detection_id`、`disguise_score` 等）。
- **预期**：视图引用的字段名与后端返回键完全匹配。
- **判定标准**：抽查绑定无失效字段；任何视图取不到值（undefined 渲染）→ FAIL P1。

#### E5【P1】响应新增字段前向兼容（18 视图全量遍历渲染）
- **操作**：浏览器带登录态遍历 18 视图（含 16 深链回归），每页等待渲染完成并捕获 console 错误；对照后端返回（如 stats.generated_at、events payload 新字段 llm_circuit_breaker）检查未知字段是否破坏渲染。
- **预期**：18 视图全部正常渲染、无 JS 错误；后端新增字段不破坏旧前端。
- **判定标准**：全遍历零 JS 异常；任一页面白屏/报错 → FAIL P1。

#### E6【P2】/ui/ SPA 深链与静态托管契约回归
- **操作**：刷新 /ui/traps、/ui/cases、/ui/dashboard 等深链可直达；`/ui/../../etc/passwd` 类穿越 → 404（B6 回归）；响应带 CSP/X-Frame-Options 头。
- **判定标准**：P2（回归确认）；穿越 404 + 安全头存在即 PASS。

### 类别 F：配置联动（4 条）

#### F1【P0】reset-key 后 WebUI/MCP/curl 三端同时失效
- **前置**：三端均以当前 key 登录/携带（WebUI 已登录页面、MCP stdio 带 AF_API_KEY、curl 会话变量）；记录旧 key。
- **操作**：`POST /auth/reset-key`（confirm+reason）→ 随后三端任意受保护请求：WebUI 轮询（stats）、MCP af_stats、curl GET /system/stats。
- **预期**：三端**立即全部 401**（unauthorized）；WebUI 自动清凭据并跳 /login；MCP isError `[unauthorized]`；curl 401。
- **判定标准**：三端 401 零例外（第 1 轮 C9 单端矩阵的**三端协同**扩展）；任何一端仍 200 → FAIL P0。

#### F2【P0】三端用新 key 重登后一致恢复
- **操作**：F1 后：浏览器重新一键登录/粘贴新 key → 页面恢复；MCP 以 AF_API_KEY=新 key 重启 stdio → af_stats 200；curl 换新 key → 200；核对 `api_keys` 表（enabled=1 恰 1 行 bootstrap）+ `GET /system/audit-verify` valid + 三端读同一数据。
- **预期**：三端重登全部恢复且数据一致；审计链在 reset 后仍完整。
- **判定标准**：三端 200 + 表状态/审计链断言全过；FAIL P0。

#### F3【P1】reset 期间 MCP 在途请求与 key 变更重启生效契约
- **操作**：① MCP 发起慢请求（如 20 万字 import 或限速路径）的同时触发 reset → 在途请求结果要么 200（验证前放行）要么 401，不出现 500/挂起；② 验证 MasterProxy 构造时固定 header（`header={"X-API-Key": key}`）→ reset 后**不重启 MCP 进程**调用 → 401；重启 MCP（环境变量新 key）→ 200。
- **预期**：在途请求确定性收尾（不悬挂）；MCP key 变更契约 = 重启生效（透传层设计语义）。
- **判定标准**：无 500/挂起；重启生效；不重启恒 401；违反 FAIL P1。

#### F4【P2】configs 无残留纪律（跨轮回归）
- **操作**：D5/D6 + F1/F3 全流程结束后直连库导出 `configs` 表，与 Phase 0 快照比对（含历史残留键清理，参照第 2 轮 E6 教训）。
- **判定标准**：configs == 快照（空 or 基线同构）；残留 canary 值记 FAIL P2（若残留影响行为升级 P1）。
