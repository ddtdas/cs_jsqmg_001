## 0. 宏观结论（TL;DR）

**系统"可运行、可用"，但"不可全自动可信"。**

架构与降级设计优秀：分级三写单事务、告警 json_extract 幂等去重（实测 0 重复）、LLM 熔断+预算+半开探活、审计哈希链（valid=true）、HITL 双确认门控、限流、脱敏强制都真实生效。LLM 未配置（`llm=not_configured`）下 3121 条检测全部完成规则分级并产出 1485 条告警——D5 降级链实证可用。

但端到端推演发现 **2 处"反诈核心闭环断裂"（P0/P1）+ 3 处数据完整性 P1**，会导致三类**静默错误**（实锤被漏、案例/证据重复、证据漏建），无人值守运行不可信：

1. **P0-1**：`job_trap_recheck` 调用 `async check_hit` 未 `await` —— 蜜饵自动踩饵检测**整个 job 静默空转**（代码确定 + 日志实证）。
2. **P1-2**：分级 L5 在全部自动路径不可达（trap_hit/account_red 从不注入），蜜饵实锤命中也不回写检测分级 → **L5=0、case_ready=0、job_case_publish 永不产出**（线上实证）。
3. **P1-3**：`job_evidence` 用 `det_ids LIKE '%id%'` 去重 → 数字前缀误判漏建证据包；evidence_packages 无唯一约束 → 重复包（实测 `[150]`×9、`[1]`×4、`[130,128]`×2 等）。
4. **P1-4**：cases 无 `UNIQUE(det_id)`、publish 不查重 → 同一检测可无限发案例（实测 det 345 有 **1125 条**、det 150 有 373 条），连锁放大在线学习 boost/gate_logs/知识蒸馏。
5. **P1-5**：双实例并存（`.venv` 与系统 Python 各一个 `app.run --port 9200` 同秒启动，仅一个持有 9200，另一个成僵尸实例持续刷 `no such table` 错误日志）——启动/运维层缺陷。

## 2. 并发 / 时序推演

Scheduler 9 job（全部 `max_instances=1, coalesce=True`，进程内无并行；实测 5 类 job 有活动日志，见 §6）：

1. **job_trap_recheck 与手工 check-hit**：job 空转（P0-1），无冲突但无功能。
2. **job_scan_dm（10min/50条）与 POST /scan/inbox（admin 手动全量消费 pending）**：两路并发消费同一 pending 集合。均无行级锁/状态条件更新（analyze_detection 直接 UPDATE status='scanned'，不校验原状态）→ **同一 pending 可能被两路同时分析**（两路都会 rule_match+LLM，双写 speech_hits/events，LLM 预算双倍消耗；幂等重写使最终状态一致，但事件/计数膨胀）。竞态窗口存在，P2。
3. **job_evidence（12h）与 POST /evidence/build**：check-then-insert 无锁 → 同 det 并发建包会重复（与 P1-3 叠加，实测重复包）。P1。
4. **job_case_publish 与 POST /cases/publish**：job 只产事件不写 cases，无冲突；人工 publish 有进程内 `_PUBLISH_LOCK`+重试（P1-D4），但**单线程锁内不查重** → 重复（P1-4）。
5. **job_persona_sim（1min）与 POST /persona/schedules/{id}/publish-now**：publish_due 与 publish_now 各自 SELECT→UPDATE published+1，无行锁 → 到期瞬间并发可**双发布同一条动态**（published 可能超 total）。P2（实测 4 条计划已 published=total，后续无到期项，窗口未触发）。
6. **job_knowledge_decay（3:30 每日）与 API harm/import**：decay 整表重算 enabled=1；与 adjust_harm 并发时 adjust 可能基于旧 decay 写 weighted，次日 job 自愈（短暂不一致，P2）；与 import_items 并发有 UNIQUE 竞态（P2-3）。
7. **job_zhihu_sync（5min）与 POST /zhihu/import**：两路都走 ingest_manual 精确哈希去重，但无唯一约束 → 并发双插入同文本（P2-2）。
8. **LLM 熔断状态机**：带锁单例，并发安全 ✅（19 次 llm_circuit_breaker 事件实证）。
9. **SQLite 写并发**：WAL + busy_timeout=5s + 请求级连接；cases.publish 额外锁。实测审计链 1823 条无锁死；**风险点**：10 万条级下 job 批量写 + 高频 scan/text 写放大（每命中词条一次 UPDATE hit_count）→ 峰值写锁等待上升，busy_timeout 5s 内不释放会偶发 "database is locked"（防御式 job 已包住，下轮重试）。

**时序风险汇总**：无死锁风险（单进程线程池 + WAL）；主要风险是**竞态双重制**（消费/建包/发布/导入 4 类 check-then-act 无原子化）+ **双实例**带来的重复执行（P1-5）。

## 4. 状态一致性推演

- **detections 状态机**（pending→scanned/processed）：自动路径 pending→scanned 闭环；**残态风险**：analyze 提交后 finalize 异常 → scanned+grade NULL 永久滞留（无重试 job 拾取 scanned，仅在事件流可发现不一致；当前 0 条）。processed 2 条 grade NULL（历史直插）。
- **traps 状态机**（draft→active→monitored→hit→retired）：状态迁移校验+事件+命中即退役实现严格 ✅；但**自动驱动断链**（P0-1）且**命中不回写检测分级/告警**（P1-2）——状态机自身一致，与检测域不一致。
- **knowledge 加权重算 vs 查询**：decay 每日 3:30 全量重算 enabled=1，daily 粒度上查询值一致；adjust_harm 并发旧 decay 窗口（P2）；import 的 decay 恒 1.0 与 refresh 口径一致 ✅。
- **evidence 哈希链 vs 源数据**：内容任何变更（重新扫描/词库删除/检测改动）→ verify TAMPERED，无重建路径（P2-7）；freeze 后一致性由链保证 ✅。
- **alerts 幂等**：json_extract 精确匹配，实测 0 重复 ✅（与 evidence 的 LIKE 形成对照）。
- **gate_logs 链**：valid=true（1823 条）✅；但 1125 条重复案例会连锁刷 gate_logs（P1-4 放大项）。

## 5. Top 风险清单（若这里出错会怎样）

### P0（核心能力失效）
- **P0-1 job_trap_recheck 未 await（scheduler.py:138 ↔ trap_engine.py:459 async check_hit）**
  出错方式：APScheduler 每 6h 调 job，`engine.check_hit(...)` 创建协程即弃，函数体零执行；try/except/break 全部失效。
  后果：蜜饵"实时反击"核心静默失效——45 个 active/monitored 蜜饵无人值守；命中事件/退役/升级检测全部不产生；系统表现"看似在跑"（日志会打印"复查 N 个蜜饵"）实则没查。日志实证：trap_hit 47 条全来自手动 API 测试（09-16 时段），调度时段无任何命中。
  修复：job 内 `await`（包 async+asyncio.run）或 check_hit 改同步（该路径无必须异步 I/O）。

### P1（数据完整性 / 反诈链断裂）
- **P1-2 L5 自动不可达 + 实锤不联动分级**
  出错方式：finalize 的 L5 条件（trap_hit>0 或 llm_fraud+conf≥0.8+account_red）在所有自动调用点（job_scan_dm/scan/text/scan/inbox/chat_import）都不注入；check_hit 命中只退役蜜饵不改检测。
  后果：最高可信信号（蜜饵实锤→L5）不进告警/证据/案例流水线；job_case_publish 每日空转（case_ready=0 实证）；L5 案例能力形同虚设。
  修复：check_hit 命中后升级触发检测（写 grade=L5+grade_reason+告警+事件，同事务或紧随事务）。

- **P1-3 证据包去重 LIKE 误判 + 无唯一约束（scheduler.py:196）**
  出错方式：`det_ids LIKE '%{det_id}%'` 对 JSON 数组子串匹配——det 1 会被 [11]/[51] 误判已有包而**漏建**；同时无 UNIQUE → 并发/手工重复建包。
  后果：证据链缺环（漏包不告警不报错）；重复包（实测 [150]×9、[1]×4、[3043]×3 等）。
  修复：json_each/EXISTS 精确判定（与 alerts 修复同款）；包表加去重约束。

- **P1-4 cases 无 det_id 唯一约束 / publish 不查重**
  出错方式：同一检测可被反复发布（含脚本/误操作）。
  后果：公开案例列表与骗术图谱被刷（实测 det 345→1125 条）；每次 publish 连锁触发 pattern weight+1（顶到 10）、知识蒸馏、gate_logs——审计链与词库权重被污染。
  修复：cases 加 UNIQUE(det_id) 或 publish 前查重（幂等返回已存在）。

- **P1-5 双实例并存（运维/启动层）**
  出错方式：同秒拉起两个 `python -m app.run --port 9200`（.venv 与系统 Python），仅一个绑定 9200，另一个成僵尸（存活不监听），其调度器持续按周期刷 `no such table`（指向空库/测试 data dir）。
  后果：日志污染（12:48/12:58/13:07/13:23 全 job 批错误）；若两实例 data dir 相同则重复处理 pending/重复发布；故障排查误导（以为主服务异常）。若再叠加端口抢占，存在双写 DB 风险。
  修复：start 脚本加端口/PID 占用检测与单实例互斥；清理僵尸 7456。

### P2（长期运维 / 质量）
- scanned 滞留 634 条（>1 天）无归档/回收策略；inbox 永不排空
- text_hash 非唯一 + 各去重口径不一 → 同文本跨源重复（实测 manual×5、zhihu×2）；hit_count 计数口径=扫描次数（非去重），在线学习信号失真
- knowledge import 并发 UNIQUE 竞态 → IntegrityError 500（未捕获）
- persona publish_due/publish_now 竞态 → 到期双发布
- IOC 提取噪声：QQ 正则 `[1-9]\d{4,10}` 匹配银行卡子串 → 虚假 QQ IOC（实测 knowledge id=4），社工库误查上游
- LLM 慢时 job_scan_dm 单轮 20-50min ≫ 10min 周期 → pending 背压（有界增长，无告警）
- evidence verify 对词库删除/检测变更敏感 → TAMPERED 且无重建路径
- unread 告警 1448/1485 无自动已读/降噪；events/gate_logs 只增无归档
