## 2. 问题清单（P0 致命 / P1 严重 / P2 建议 / P3 锦上添花；共 23 条）

> **P0（致命）：0 条。** 未发现系统级崩溃、数据损坏或核心功能（R1–R6）不可用的缺陷；112 用例全绿、主控可正常启动运行。最严重的问题集中在"认证/审计/状态管理"层级，判定为 P1。

### P1-1 敏感写操作端点无 admin 认证（docs/README 标 🔒 但代码开放，已实测复现）【严重】
- 【位置】`app/api/cases.py:28-33`（POST /cases/publish）、`app/api/config.py:82-124`（PUT /config）、`app/api/traps.py:65-86`（deploy/monitor/disable/retire）、`app/api/evidence.py:26-46`（build/freeze/export）、`app/api/scan.py:60-85`（POST /scan/inbox）
- 【问题】主方案 §11 D6「bootstrap admin key + 敏感操作 confirm+reason」要求下，**实测**：无 X-API-Key 直接 `POST /api/v1/cases/publish` → **HTTP 200 入库**；`PUT /api/v1/config`（confirm=true）→ **HTTP 200 改写配置并写 gate_logs**；`POST /api/v1/traps/{id}/disable|retire`、`POST /evidence/{id}/freeze` 均无认证拦截。而 `README.md:184/188`、`docs/02-API.md:22-26/37-43/55` 明确标注这些端点 🔒（需 admin key）——承诺与实现系统性背离。全项目 `require_admin` 仅挂在 system.stats / zhihu login/verify/import（`app/api/system.py:45`、`app/api/zhihu.py:68/88/113`）三处。
- 【建议修复方案】① 上述端点统一加 `dependencies=[Depends(require_admin)]`；② `POST /cases/publish` 与 `POST /traps/{id}/retire` 增加 confirm/reason 请求模型（见 P1-5）并写 gate_logs；③ 补充 pytest 负例：无 key → 401、错误 key → 401。
- 【影响】任何能访问 127.0.0.1:9200 的本地进程/同网段用户可发布案例、改阈值、退役蜜饵、冻结证据——审计链被绕过，D6 承诺落空，文档安全边界失真。

### P1-2 退饵/发布案例缺 confirm+reason 双确认闸控（MCP 透传参数被静默丢弃）【严重】
- 【位置】`app/api/traps.py:83-86`（retire 端点无 Body 模型，`payload` 参数不存在）、`app/api/cases.py:21-33`（PublishCaseRequest 无 confirm/reason 字段，Pydantic 默认忽略未知字段）、`app/api/config.py:31-36`（唯一有 confirm+reason 的端点，见 P1-1 缺认证）、`mcp/server.py:209-214`（af_retire_trap 传 confirm+reason）、`mcp/server.py:307-326`（af_publish_case 传 confirm+reason）
- 【问题】主方案 §11「危险动作（退饵/改配置/入库发布）需 confirm=true + reason≥20，GateLog 哈希链审计」：改配置已实现 confirm+reason（无认证）；但**退饵与发布案例完全没有闸控**——MCP 层 `af_retire_trap`/`af_publish_case` 把 confirm/reason 透传给主控，主控端点不解析请求体（retire 无 Body 模型）或模型无此字段（publish），参数被**静默丢弃**，操作照常执行且不产生 gate_logs（实测 gate_logs 仅 config.put 一类）。
- 【建议修复方案】① retire/publish 端点增加 `{confirm: bool = False, reason: str = ""}` 请求模型，校验 confirm=true 且 reason.strip()≥20 字（422/403 封包）；② 操作成功后写 `gate_logs`（action='trap.retire'/'case.publish'，before/after/payload_hash）+ events；③ mcp/server.py 无需改（透传即生效），但补端到端 pytest 验证 confirm 参数真正拦截。
- 【影响】关键敏感操作无确认环节，误操作/自动化误触发无法追溯；MCP 文档宣称「敏感操作需 confirm+reason 由主控闸控」为虚假承诺。

### P1-3 LLM 熔断与日预算状态在真实运行中永不生效（每请求新建 Provider 实例）【严重】
- 【位置】`app/services/llm_provider.py:252-263`（`get_provider()` 每次 `LLMProvider(...)` 新建实例，无缓存/单例）、调用点 `speech_engine.py:124`、`trap_engine.py:246/264`、`desensitize.py:106`
- 【问题】`degraded` / `failed_streak`（MAX_FAIL_STREAK=3 熔断）/ `used_today`（daily_budget 预算）都是**实例字段**，而每个扫描请求都会新建一个全新 Provider → 熔断计数与预算计数永远从 0 开始。D5「连续 3 次失败自动熔断并告警」与 §6.3「每日次数上限预算护栏」**在真实运行中不存在**（单测因构造单实例而全绿，掩盖了问题）。
- 【建议修复方案】① `get_provider()` 改为模块级懒加载单例（`lru_cache`/模块变量 + 进程锁），或把熔断/预算状态提升为模块级状态（dataclass + threading.Lock）；② daily_budget 按自然日滚动计数；③ 补集成级测试：同一进程内连续 N 次失败后第 N+1 次调用直接 DegradedError。
- 【影响】LLM 配置后 `/scan/text` 可被无限触发，成本无上限；熔断不生效时在 LLM 服务故障期间每次请求都白等超时（30s），体验与 D5 承诺不符。

### P1-4 知乎"全局"令牌桶与指数退避实际为每请求实例（合规频率控制失效）【严重】
- 【位置】`app/api/zhihu.py:25-27`（`_bridge()` 每次请求新建 `ZhihuBridge`）、`app/services/zhihu_bridge.py:310-325`（`self.limiter`/`self.backoff` 为实例字段）
- 【问题】主方案 §5.4/§11「全局令牌桶（默认 20 请求/分）+ 失败指数退避」：TokenBucket/BackoffManager 随 Bridge 每请求重建，**每请求都是满桶、退避状态清零**，"全局"限速在真实请求链中失效（仅单请求内多次调用有效）。单测 `test_token_bucket_*`/`test_backoff_*` 用独立实例，无法暴露该问题。
- 【建议修复方案】① TokenBucket/BackoffManager 提升为模块级单例（容量从 `settings.zhihu_rate_limit` 读取，测试可重置）；② 或挂到 `app.state.limiter` 由依赖注入；③ 补 API 级测试：连续请求超过配额后第 N+1 次被 429/拒绝。
- 【影响】知乎合规红线「频率控制」名存实亡，可能触发平台反爬风控、账号受限；退避失效导致失败通道被持续打爆。
