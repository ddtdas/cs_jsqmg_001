## 类别 A：全流程实战串联（10 条）

> 目标：不是逐端点测，而是模拟真实用户/agent 的完整高价值流程；**每条流程 = 成功路径 + 至少 1 个失败/异常路径**。

### A1. 反诈主流程 · 成功路径（P0）
【操作】① `POST /auth/local-login`（回环）取 key → ② `POST /zhihu/import` 导入诈骗文本（杀猪盘 + 手机号 13800138000 + 唯一时间戳）→ ③ `POST /scan/inbox`（admin）批量消费 → ④ `GET /grading/explain/{detection_id}` → ⑤ `GET /alerts?unread_only=true` 出现未读 → ⑥ `POST /alerts/{id}/read` → ⑦ `GET /scan/inbox`（admin）确认原文入链 → ⑧ `GET /events` 检索全部动作事件。
【预期】每一步 200/封包 ok；inbox `processed≥1` 且首条 `verdict≠normal`；explain 返回 `grade_reason` 证据链 ≥1 条；L3+ 产生未读告警且 read 后 `unread=0`；events 中能看到 `detection_scanned/alert_created/alert_read` 类记录。
【判定标准】全链路 8 步全部通过；任一步 500/缺事件记录 → P0；evidence 链路见 A3。

### A2. 反诈主流程 · 失败/异常路径（P0）
【操作】复跑 A1 的②，**原样重复同一文本**（含相同时间戳）→ 观察 `ingested/duplicates` → 再导入**空 source 非法值**（`source:"hacker"`）与 **from_url_name 超 120 字符**。
【预期】重复导入：`ingested=0, duplicates=1`（sha256 去重）；非法 source → 422（pattern 校验）；from_url_name 121 字符 → 422。
【判定标准】去重语义正确（不双写 pending）；两次非法请求均 4xx 且不产生检测记录（`GET /scan/inbox` 计数不增）→ 否则 P1。

### A3. 证据链 · 成功路径（P0）
【操作】`POST /evidence/build`（admin，det_ids 取 A1 的 detection_id）→ `GET /evidence/{pkg_id}`（verify）→ `POST /evidence/{pkg_id}/freeze`（admin）→ `GET /evidence/{pkg_id}/export?fmt=json` + `fmt=text`（admin）→ `GET /evidence/{pkg_id}/report-template?kind=96110|platform|pibyao`。
【预期】build 200 返回 pkg_id；verify `intact=True`；freeze `frozen=True`；export 两种格式均 200 且内容一致（同包同数据）；三模板 200、含"个人"署名、不含手机号明文、无"已受理/已冻结"官方措辞。
【判定标准】全链通过；freeze 后 export 内容与 freeze 前一致（哈希链不可变）；模板合规三查（署名/无明文/不冒充）→ 任一违反 P0。

### A4. 证据链 · 失败/异常路径（P0）
【操作】① build 传 `det_ids=[]` → ② build 传不存在 id（`det_ids=[999999]`）→ ③ freeze 一个不存在的 pkg（`/evidence/999999/freeze`）→ ④ export `fmt=pdf`（非法）→ ⑤ report-template `kind=official`（非法）→ ⑥ 对**同一 pkg 连续 freeze 两次** → ⑦ export **未冻结**的新包。
【预期】① 422（minItems=1）；②/③ 4xx 统一封包 error.code（不得 500，不得静默建空包）；④/⑤ 422（pattern 校验）；⑥ 第二次 freeze 返回 200 幂等 **或** 409 冲突，但绝不 500、`frozen` 状态不翻转；⑦ 未冻结包可导出但响应须能区分未冻结状态（观察项，若与冻结包无任何区分记为 P2）。
【判定标准】无 500；无幽灵数据（不存在的 pkg 不产生 events 写入）；②/③ 若 200 且建了空包 → P1。

### A5. 案例发布+图谱 · 成功路径（P0）
【操作】`POST /cases/publish`（admin，det_id=A1 检测，redacted_payload 用 `DesensitizeService().regex_redact()` 脱敏后的文本，graph_tags=["fake_investment"]，confirm=true，reason≥20 字）→ `GET /cases?tag=fake_investment` → `GET /cases/graph` → `GET /events?kind=case_published`。
【预期】publish 200 返回 case_id；按 tag 查询 total≥1；graph `by_tag` 含 fake_investment 计数 +1；events 有 `case_published` 记录；`gate_logs` 新增 `action='case.publish'` 审计行（含 64 位 payload_hash）。
【判定标准】入库、图谱、事件、审计四者一致（case 数/图谱数/事件数联动）；缺任一 → P1。

### A6. 案例发布 · 脱敏绕过失败路径（P0）
【操作】依次用以下载荷 publish（confirm=true + reason 合规）：① 明文手机号 `13812345678`；② **嵌套 JSON 字符串** `{"phone":"13812345678","note":"加我微信"}`；③ **JSON 字符串内嵌** `加我微信"13812345678"稳赚不赔`；④ **Unicode 变体**：全角数字 `１３８１２３４５６７８`、零宽字符插入 `138\u200b1234\u200b5678`、字母数字混淆 `l38l2345678`；⑤ **身份证号** `110101199003074512`；⑥ 微信/QQ 号 `wxid_abc123`、`123456789`（纯数字 9 位）。
【预期】①–⑤ 全部 422 `sensitive_data` 拒绝入库；⑥ 视实现判定（微信 ID 若被放行属设计边界，记录为观察项，但**手机号/身份证任何变体放行 = P1 脱敏漏洞**）。
【判定标准】cases 表条数不因 ①–⑤ 增加；⑥ 记录通过/拒绝结果与 redacted 依据；若任一手机号变体成功入库 → **P1（强制脱敏红线失守）**。

### A7. MCP 全链路（成功路径，P0）
【操作】以 venv 加载 `mcp/server.py`（真实 HTTP MasterProxy 指向 127.0.0.1:9200 + 当前 key），顺序调用：`af_scan_text`（诈骗话术）→ `af_list_scan_hits` → `af_build_evidence`（det_ids 取上一步 detection_id）→ `af_freeze_evidence` → `af_export_evidence`（json+text）→ `af_report_template`（kind=96110）→ `af_list_events` 验证全链事件。
【预期】每步返回与 REST 等价的数据（verdict/grade、pkg_id、frozen、模板文本）；MCP 是纯透传，不得出现第二套业务逻辑（响应字段与 REST 一致）。
【判定标准】7 步全通过且字段与 REST 同构；若 MCP 响应与 REST 语义不一致 → P1（D1 铁律破坏）。

### A8. MCP 全链路（失败/异常路径，P0）
【操作】① `af_publish_case` **不带 confirm**（仅 det_id+redacted_payload）→ ② `af_config_update` 带 confirm=true 但 reason="短" → ③ `af_retire_trap` 对 active 蜜饵 confirm=false → ④ `af_scan_text` 传空文本 → ⑤ `af_get_evidence` 传不存在 pkg。
【预期】①/③ → 403 `confirm_required` 透传；② → 422 `reason_too_short` 透传；④ → 422；⑤ → 404 封包透传。全部不 500、不透传成 200。
【判定标准】MCP 闸控与 REST 完全一致（错误 code 透传）；若 MCP 端吞掉错误返回 200 → **P0**（agent 会误以为操作成功）。

### A9. 账号速查→踩饵→画像联动（P1）
【操作】① `POST /accounts/check`（url_name=唯一名，signals 含 `reported_count:3, trap_hit_ids:[A1 命中蜜饵 id]`）→ ② `GET /accounts/{url_name}` 建画像 → ③ 新生成蜜饵 draft→deploy→monitor → ④ 用**改写 5-10 字**变体文本 `check-hit` 踩饵 → ⑤ `GET /accounts/{account_id}/timeline` 复查。
【预期】check 返回 `risk_level∈{green,yellow,red}` 且有证据链；踩饵 `hit=True` 且蜜饵立即 retired；timeline 200 且包含画像更新与踩饵记录。
【判定标准】命中即退役 + timeline 可追溯；若踩饵命中但蜜饵未 retired → P1（状态机破坏）；timeline 无记录 → P2。

### A10. 会话历史/供应链接入（P1）
【操作】① WebUI 侧边栏「会话历史」展开 → 数据源 = `/scan/hits`(6) + `/events`(6) + `/traps?status=hit`(6) 聚合（15s 轮询）→ ② 点击条目跳 `/sessions?tab=xxx&id=yyy` 定位（tab=hit|event|trap|alert）→ ③ 打开详情抽屉调 `/grading/explain/{id}` → ④ 供应链页 SupplyChainView 调 `POST /accounts/check` + `GET /accounts/{id}/timeline`。
【预期】侧边栏聚合列表与 API 数据一致；深链定位打开对应详情（异步轮询兜底 8s）；供应链页真实数据渲染（account_id 复用 A9 的）。
【判定标准】真实浏览器操作可复现（若环境无浏览器二进制，降级为 client.js 端点映射 + HTTP 探测核对，并注明"浏览器侧未实测"）；7 新页端点映射与 openapi 无"调了不存在的端点"→ 否则 P2。

## 类别 B：边界与极端输入（10 条）

> 目标：超长/空/异形/恶意输入矩阵。基准：Pydantic 约束见 docs/openapi.json（scan/text text 1–20000；import text 1–200000；create trap bait_text 4–2000；check-hit text 1–20000；publish redacted_payload 1–10000；login cookie 1–64000；accounts url_name 1–200）。

### B1. 超长文本边界（P0）
【操作】`POST /scan/text`：① 恰好 **20000 字符**正常语料（`"测"*20000`）→ ② **20001 字符** → ③ `check-hit` 恰好 20000 / 20001。
【预期】① 200 且 verdict=normal（规则不命中，不超时）；② 422 `string_too_long`；③ 同上分界。
【判定标准】边界严格生效（20000 过、20001 拒）；20000 字符请求不得超时/崩（响应 < 5s）；超界请求不产生检测记录。

### B2. 十万字导入与超限（P0）
【操作】`POST /zhihu/import`：① 构造 **10 万字符**文本（`"冒充客服退款诈骗"*10000` + 唯一后缀）→ ② 20 万字符 → ③ **20 万 + 1** 字符 → ④ from_url_name=121 字符。
【预期】① 200 `ingested≥1`（100,000 ≤ 200,000 上限）；② 200（恰在上限）；③ 422；④ 422。
【判定标准】①/② 不超时（< 10s）不崩、pending 入链 1 条；③/④ 4xx 且无写入；扫描时 `GET /scan/inbox` 能看到该长文本（截断展示可接受，原文入库为准）。

### B3. 空/纯空白输入（P1）
【操作】`POST /scan/text`：① `text=""` → ② `text="   "`（3 空格）→ ③ `text="\n\t "` → ④ `check-hit` text 同 ①–③ → ⑤ `accounts/check` url_name=""。
【预期】①/⑤ 422（minLength=1）；②/③ 200 verdict=normal（空白无规则命中，不崩）；④ 空白不命中（hit=False）。
【判定标准】无 500；空白文本不得误判为诈骗；若 ②/③ 返回 422 也接受但记录（属防御性校验，非缺陷）。

### B4. 纯 emoji / 异形符号（P1）
【操作】`POST /scan/text`：① 纯 emoji `😀😁😂🤣😊😍🥰😘` → ② emoji+诈骗词 `杀猪盘🚀🚀🚀稳赚不赔💰` → ③ 颜文字 `(╯°□°)╯︵ ┻━┻` + 零宽字符 `\u200b\u200c` → ④ `accounts/check` url_name 全 emoji。
【预期】①/③ verdict=normal 不崩；② verdict≠normal（规则词命中不受 emoji 干扰）；④ 200 或 422 均可（url_name 校验），不 500。
【判定标准】无 500/崩溃；emoji 不导致规则引擎异常；② 若误判 normal → P2（规则召回缺口记录）。

### B5. SQL 注入字符串（P0）
【操作】`POST /scan/text`：`'); DROP TABLE detections; --`、`' OR 1=1 --`、`" UNION SELECT * FROM api_keys --`、`稳赚不赔'; DELETE FROM alerts; --`。随后 `GET /scan/hits` 与 `GET /system/stats`（admin）验证数据库完好。
【预期】全部 200/422（按文本内容判定或校验拒绝），**绝不 500**；DB 完好：`/scan/hits` 正常返回、stats 计数可用、`api_keys` 表仍存在（间接：旧 key 仍有效）。
【判定标准】注入串不改变任何表（对比 A 类执行前 stats 基线）；若出现 500 或数据表被删/篡改 → **P0**。

### B6. 裸 HTML/JS（XSS 回显检查，P0）
【操作】① `POST /zhihu/import` 文本含 `<script>alert(document.cookie)</script>` 与 `<img src=x onerror=alert(1)>` → ② `POST /scan/inbox`（admin）消费 → ③ `GET /scan/inbox`（admin）与 `GET /scan/hits` 查看回显 → ④ 同一载荷走 `cases/publish`（脱敏后）。
【预期】③ 响应 `Content-Type: application/json`、内容为 JSON 封包（HTML 作为字符串原样存在但**不被浏览器解析执行**——API 侧只需验证 content-type 与封包结构；WebUI 侧由 Vue 默认转义兜底）；④ 不含手机号则 200 入库、`GET /cases` 回显同 JSON 语义。
【判定标准】API 响应头 `application/json` + 无裸 HTML 注入（如 `<script>` 出现在非字符串位置或破坏 JSON 结构 → P0）；前端渲染转义属 webui-dev 验证点（有浏览器则实测无弹窗，无浏览器则标注待验）。

### B7. 误格式 body（null/数组/对象/裸字符串，P1）
【操作】对 `scan/text`、`evidence/build`、`cases/publish`、`config PUT`、`accounts/check` 各发：① body=`null` → ② body=`[1,2,3]`（数组）→ ③ body=`"字符串"`（裸字符串）→ ④ body=`{}`（缺必填字段）→ ⑤ body=`{"text": 123}`（类型错误）。
【预期】全部 **422**（FastAPI 校验层拒绝），无 500；④/⑤ 报缺失/类型错误明细。
【判定标准】5 端点 × 5 载荷 = 25 组合全部 4xx 且无 500；若个别端点 500（如反序列化裸字符串崩溃）→ **P1**。

### B8. 非常规 UTF-8（P2）
【操作】`POST /scan/text`：① 前置 BOM `\ufeff` 的文本 → ② 组合字符 `e\u0301`（é 分解形式）→ ③ 右到左控制符 RTL `\u202e` 包裹诈骗词 → ④ 代理对/生僻字 `𠀀𠀁` 混合诈骗词。
【预期】全部 200 不崩；规则词仍可命中（② 若因规范化不命中则记录为 P2 规则缺口，不判崩溃）；① BOM 不导致 text_hash 去重异常。
【判定标准】无 500；检测记录正常写入；RTL/生僻字不产生乱码入库异常。

### B9. 重复提交幂等矩阵（P0）
【操作】① `zhihu/import` 同文本 ×2 → ② `alerts/{id}/read` 同告警 ×2 → ③ `scan/text` 同文本 ×2 → ④ `cases/publish` 同 det_id ×2（脱敏载荷）→ ⑤ `freeze` 同 pkg ×2（与 A4⑥ 复用）。
【预期】① 第二次 `ingested=0, duplicates=1`；② 两次均 200 且第二次后 `unread` 仍 0、`events` 无重复 read 事件（或事件可幂等解释）；③ 两次均 200 且 `detection_id` 不同（**属设计行为**：scan 不按内容去重，仅记录）；④ 两次 200 生成 2 条案例或第二次 409（实现二选一皆可，记录实际）；⑤ 见 A4⑥。
【判定标准】无 500；①/② 严格幂等（不双写 pending、不重复告警事件）；③ 两条检测属预期，不判缺陷；④ 若第二次生成重复案例且无任何提示 → P2 观察项。

### B10. 并发重复 check-hit（双请求同一蜜饵，P0）
【操作】准备 1 个 monitored 蜜饵（唯一 bait_text，改写 5-10 字变体做命中文本）→ 用两个线程**几乎同时**发 `POST /traps/{id}/check-hit`（同一文本）→ 随后查 `GET /traps/{id}` 与 `GET /events?kind=trap_hit`。
【预期】主控不崩、无 500；蜜饵最终 `status=retired`；`hit_count` **不双写**（=1）；`trap_hit` 事件仅 1 条（或 2 条但 `trap_retired` 事件仅 1 条）。
【判定标准】双请求后 hit_count==1 且 retired 事件仅 1 条 → 通过；若 hit_count==2 且产生 2 条 retired 事件 → **P1 并发缺陷**（报告不阻塞，交 backend-core）；任何 500/崩溃 → P0。

## 类别 C：数据一致性与状态机压力（9 条）

> 状态机（trap_engine.py）：`draft→{active,retired}`；`active→{monitored,retired}`；`monitored→{hit,retired}`；`hit→{retired}`；`retired→∅`；check-hit 仅接受 active/monitored；disable 仅 active/monitored；retire 需 confirm+reason（API 层）。

### C1. 状态机非法迁移攻击 ①：跳过 deploy 直 retire / 直 monitor（P0）
【操作】新建 draft 蜜饵：① 直接 `POST /traps/{id}/retire`（confirm=true+reason 合规）→ ② 另建 draft 直接 `POST /traps/{id}/monitor` → ③ 另建 draft 直接 `POST /traps/{id}/disable`。
【预期】① 200 retired（`draft→retired` 合法迁移，retired_reason=user）——**注意这是合法路径**，判定在审计：必须写 `gate_logs action='trap.retire'`；② 400 非法迁移封包（`active` 才可 monitor）；③ 400（仅 active/monitored 可 disable）。
【判定标准】②/③ 400 且蜜饵状态不变（仍 draft）；① 有 gate_logs 审计；若 ②/③ 被放行改状态 → **P0 状态机漏洞**。

### C2. 状态机非法迁移攻击 ②：重复 deploy / 重复 monitor / 退役后再动（P0）
【操作】① active 蜜饵再 `deploy` → ② monitored 蜜饵再 `monitor` → ③ retired 蜜饵再 `deploy` / `monitor` / `disable` / `retire`（confirm 合规）→ ④ active 蜜饵直接 `check-hit`（不先 monitor）。
【预期】①② 400（无自环迁移）；③ 全部 400/409 拒绝（终态不可逆）；④ 200 且命中后 `active→monitored→hit→retired`（隐式迁移，`transition` 字段应标明）。
【判定标准】非法迁移全部被拒且状态不漂移；④ 的隐式迁移事件链完整（trap_monitored(implicit)→trap_hit→trap_retired）；retired 后任何写路径都不复活 → 否则 P0。

### C3. retired 蜜饵再 check-hit（P0）
【操作】对 C2 已 retired 蜜饵再发 `check-hit`（命中文本）→ 再发 `disable`。
【预期】`check-hit` → 409 `trap_retired`（"不再监测"）；`disable` → 400。状态保持 retired、hit_count 不变。
【判定标准】409/400 封包 + 状态不漂移；若命中文本在 retired 蜜饵上再次命中并改变状态 → **P0**（命中即退役防线失效）。

### C4. draft 蜜饵 check-hit（P1）
【操作】对未部署 draft 蜜饵发 `check-hit`（含命中文本）。
【预期】400 `未部署的蜜饵不可检测踩饵`（或等效错误码封包）；draft 状态不变、hit_count=0。
【判定标准】4xx + 无状态变化；若 draft 被命中并退役 → P1（未部署蜜饵被消费）。

### C5. disable 蜜饵矩阵（P1）
【操作】① active 蜜饵 `disable` → 状态/`enabled` 字段 → ② disabled 蜜饵 `check-hit` → ③ disabled 蜜饵 `deploy`/`monitor` → ④ disabled 蜜饵 `retire`（confirm 合规）。
【预期】① 200 enabled=0；② 409 `trap_disabled`；③ 400；④ 200 retired（disable 不阻塞退役，终态迁移合法）。
【判定标准】②/③ 被拒且状态不漂移；④ 退役成功且写 gate_logs；若 disabled 蜜饵仍可被 check-hit 命中 → P1。

### C6. 冻结后写路径全矩阵（P0）
【操作】冻结 pkg X（A3 产物）：① `freeze` 再 ×1 → ② `export` json+text ×2（前后一致性）→ ③ `GET /evidence/{id}` verify → ④ `report-template` ×3 → ⑤ 尝试用 X 关联新检测（无此类端点，则验证**无写路径可改包**：对比 freeze 前后 export 的 sha256）→ ⑥ 用 X 的 det_id 再 build 新包 Y → 对比 X/Y。
【预期】① 幂等/409（不翻转 frozen）；② 两次 export 内容逐字节一致（哈希链不可变）；③ intact=True 恒定；⑥ Y 是独立新包、X 不受影响。
【判定标准】freeze 前后 `sha256(export json)` 完全一致；X/Y 相互独立；若 freeze 后内容可变（export 两次不一致）→ **P0 证据链失效**。

### C7. 案例脱敏绕过矩阵（与 A6 互补，聚焦"防绕过深度"，P0）
【操作】publish 载荷依次为：① `{"nested":{"phone":"13812345678"}}`（深层嵌套对象）→ ② `[{"phone":"13812345678"}]`（数组）→ ③ JSON 字符串转义 `"{\"phone\":\"13812345678\"}"` → ④ 中文大写数字 `一三八一二三四五六七八` 附"电话"语义 → ⑤ 手机号拆词 `138-1234-5678`、`138 1234 5678`、`+8613812345678` → ⑥ 前后缀混淆 `a13812345678b`。
【预期】①–③ 若按字符串整体正则脱敏校验 → 422 拒绝；④–⑥ 视实现（正则覆盖度不同），**至少 ①/③ 中任一被放行即 P1**（嵌套/转义绕过），⑤ 的 `+86` 前缀或分隔符变体被放行 → P1。
【判定标准】记录每载荷的通过/拒绝结果 + 判定依据（regex vs LLM 层）；凡 138 段 11 位数字变体成功入库 → P1；全部拦截 → 通过。

### C8. 告警 read 幂等与计数一致（P1）
【操作】① `GET /alerts?unread_only=true` 记 N → ② read 其中 3 条（含同一条 ×2）→ ③ 复查 `unread=N-3`（不是 N-2）→ ④ `GET /alerts?level=L5` 过滤 → ⑤ `limit=501`（超上限）→ ⑥ `limit=0`。
【预期】③ 幂等正确；④ 只返回 L5；⑤ 422（limit≤500）；⑥ 422（limit≥1）。
【判定标准】重复 read 不重复扣减；非法 limit 4xx；若重复 read 使 unread 多减 → P1。

### C9. reset-key 后旧 key 全端点失效矩阵（P0）
【操作】① 记录旧 key → ② `POST /auth/reset-key`（confirm=true + reason≥20）→ ③ 用**旧 key** 依次调：`GET /system/stats`、`POST /scan/inbox`、`GET /scan/inbox`、`POST /evidence/build`、`POST /traps/generate-draft`、`POST /zhihu/import`、`PUT /config`、`POST /cases/publish` → ④ 用**新 key**（重读文件）调同 8 端点 → ⑤ 查 `gate_logs`（auth.reset_key 行：before/after 均 key_sha256）+ `events`（admin_key_reset）+ `api_keys`（旧 enabled=0/新 enabled=1）。
【预期】③ 全部 401 `invalid_api_key`；④ 全部 200/相应成功；⑤ 审计三表齐全。
【判定标准】**8×2 全矩阵零例外**；任一受保护端点旧 key 仍可用 → **P0**；审计缺任一表记录 → P1。⚠️ 执行顺序：放在类别 D 最后（reset 后后续用例统一换新 key；若测试中多次 reset，每次都要重读 key 文件）。

## 类别 D：认证与越权边界（8 条）

### D1. bootstrap-info 不泄 key（P0）
【操作】`POST /auth/bootstrap-info` → 检查响应体与响应头：① 无 key 明文/前 9 位前缀 → ② 无 key 文件路径 → ③ 无 `api_keys` 表内容。
【预期】仅返回 `initialized` 等布尔/提示信息；任何字段不得含 `af_admin`、`bootstrap_admin_key`、盘符路径。
【判定标准】响应体全文正则扫描 `af_admin|bootstrap|\.txt|C:\\` → 0 命中；命中任一 → **P0 信息泄露**。

### D2. local-login 回环绕过矩阵（P0）
【操作】`POST /auth/local-login` 附带：① `X-Forwarded-For: 203.0.113.9` → ② `X-Real-IP: 203.0.113.9` → ③ `X-Forwarded-Host: evil.example.com` → ④ `X-Client-IP: 203.0.113.9` → ⑤ `X-Forwarded-For: 127.0.0.1`（伪装回环）→ ⑥ `Forwarded: for=203.0.113.9` → ⑦ 重复 XFF 头（`X-Forwarded-For: 203.0.113.9` 两次）。
【预期】①/②/④/⑥/⑦ 全部 **403 `loopback_only`**（仅信任真实 TCP 来源）；③ 200 返回 key（Host 头不参与来源判定，基线 3.3 已证）；⑤ 关键刁钻点：**即使 XFF 写 127.0.0.1 也必须 403**（伪造回环）。
【判定标准】⑤ 若返回 key → **P0 认证绕过**；④/⑥ 若返回 key → **P0**（非标准头被信任）；③ 200 属设计行为不判。

### D3. current-key / reset-key 回环矩阵（P1）
【操作】`GET /auth/current-key` 与 `POST /auth/reset-key`（confirm 合规）各带：① XFF 非回环 → ② X-Real-IP 非回环 → ③ 无任何头（本机直连）。
【预期】①② 403 `loopback_only`；③ 200（current-key 返回 key 明文，reset-key 返回审计）。
【判定标准】与 D2 同规则；③ 返回的 current-key 必须与 `data/bootstrap_admin_key.txt` 一致 → 不一致 P1。

### D4. 限流 429 与 admin 豁免（P0）
【操作】默认 `AF_RATE_LIMIT_PER_MIN=60`（app/config.py）：① 无 key 快速连发 `POST /scan/text` 61 次（同文本）→ 第 61 次应 **429 `rate_limited`** → ② 429 后带 admin key 再发 → 200 豁免 → ③ `GET /traps`（非限流热路径）不受影响 → ④ 限流窗口后（约 60s 或调低配额重启验证）恢复。
【预期】① 前 60 次 200、第 61 次 429；② 200；③ 200；④ 恢复 200。
【判定标准】429 封包 `{ok:false,error:{code:"rate_limited"}}`；admin 豁免生效；若 60 次内提前 429（计数错误）→ P2；若带 key 仍被 429 → **P1**（豁免失效）。提示：为加速可临时以 `AF_RATE_LIMIT_PER_MIN=3` 重启主控验证（test_p2 已覆盖此路径，本轮以默认 60 实测一次为准）。

### D5. sessionStorage 登录态切换（P1）
【操作】① 浏览器登录 `/ui/` → DevTools 验证凭据存于 **sessionStorage**（非 localStorage）→ ② 手动把 `sessionStorage.af_api_key` 改成垃圾值 → 刷新 → 观察路由守卫 → ③ 改成有效 key → 刷新 → 观察 → ④ 关闭浏览器标签重开 → 观察登录态。
【预期】② 跳 `/login?redirect=...`（守卫拦截无效 key）；③ 进入仪表盘且数据加载；④ 登录态消失（sessionStorage 会话级，关闭即失效）→ 需重新一键登录。
【判定标准】凭据存储介质为 sessionStorage（代码核对 `webui/src`）；无效 key 被守卫拦截且 API 401 不炸页面；若为 localStorage（持久化）→ **P1 安全缺陷**。无浏览器环境则降级为源码核对 + 标注待真机验证。

### D6. 越权访问矩阵（公开 vs 受保护，P0）
【操作】无 key 依次调：① `GET /system/stats` → ② `POST /scan/inbox` → ③ `GET /scan/inbox` → ④ `POST /zhihu/import` → ⑤ `POST /evidence/build` → ⑥ `GET /evidence/1/export` → ⑦ `POST /traps/generate-draft` → ⑧ `PUT /config` → ⑨ `POST /cases/publish` → ⑩ `POST /alerts/1/read`（公开对照）→ ⑪ `POST /zhihu/channels/ch_a/login`。
【预期】①–⑨/⑪ 全部 **401 `missing_api_key`** 统一封包；⑩ 200（read 公开）。
【判定标准】10 个受保护端点全 401 封包合规；任一 200 → **P0 越权**；⑩ 若 401 → 属收紧，记录观察（非缺陷）。

### D7. 错误 key 格式矩阵（P1）
【操作】带 key 调 `GET /system/stats`：① key=""（空）→ ② `af_admin_`（无后缀）→ ③ `admin123`（无前缀）→ ④ 200 字符超长 key → ⑤ 前后带空格 ` af_admin_xxx ` → ⑥ key 放 `Authorization: Bearer`（README 称支持）→ ⑦ key 放 query 参数 `?x-api-key=...`。
【预期】①–⑤ 全部 401 `invalid_api_key`；⑥ 200（Bearer 支持）；⑦ 401 或 200（实现未声明 query 传参，记录实际——若 200 记观察项：query 泄 key 风险 P2）。
【判定标准】无 500；⑥ 按文档生效；若 ⑤ 空格 key 被放行（未 strip）→ P2。

### D8. 限流键与伪造来源头（P2 刁钻观察）
【操作】打满限流（同 D4，60 次无 key 429 后）→ 带 **XFF 非回环头**再发 `scan/text`（无 key）→ 观察是否仍 429。
【预期】仍 429（限流键按真实 TCP 来源，不信任 XFF）；若带 XFF 后绕过 429 → **P1**（伪造来源可打穿限流，且与 D2 的 loopback 判定规则矛盾——应一并上报）。
【判定标准】记录 XFF 对限流键的影响；结果二选一必须与 D2 的"仅信任 TCP 来源"语义自洽，自相矛盾即 P1。

## 类别 E：稳定性（4 条）

### E1. 50 次混合压力（P0）
【操作】同一主控：① 顺序 25 次 `POST /scan/text`（诈骗/正常交替，带时间戳）→ ② 25 次 `check-hit`（对 5 个 monitored 蜜饵轮换 + 不存在的 trap_id 混合）→ ③ 其中 10 次用 2 并发线程发。
【预期】所有请求返回 200/4xx 合理状态；**无 500、无连接重置、主控进程不退出**；5 个蜜饵中被命中者正常 retired。
【判定标准】请求失败率 0（除预期的 404/409/429）；任一 500/进程退出 → **P0**；压力后 health 立即 200（见 E2）。

### E2. 压力后计数一致性（P1）
【操作】E1 前后各取 `GET /system/stats`（admin）对比：detections 增量 == 25 条 scan 实际写入数；alerts 增量 == L3+ 新增数；蜜饵命中数 == retired 新增数。
【预期】计数严格对账（统计口径=表真实计数，P2-1 已证）。
【判定标准】任一对账差异 → P1（计数漂移）；`generated_at` 存在且为本次时间。

### E3. 日志无堆栈、有请求记录（P0）
【操作】E1 结束后：① 对比 `var/logs/app.log` 新增部分（以 Phase 0 基线行号为界）→ ② grep `Traceback|ERROR|CRITICAL` → ③ grep `scan/text` 请求日志行 → ④ 检查无敏感信息（key 明文/密码/cookie 原文）落入日志。
【预期】② 0 命中（预期 4xx 业务拒绝不属于 ERROR 堆栈）；③ 有 `method=POST path=/api/v1/scan/text status=200/4xx` 类记录；④ 无 `af_admin_` 明文、无 cookie 原文。
【判定标准】堆栈 0；请求日志齐全；日志含 key 明文 → **P1 敏感信息落盘**（立即交 backend-core）。

### E4. 调度器 6 job 无异常（P1）
【操作】① 用 venv 执行 `from app.services import scheduler; scheduler.job_snapshot()` → 断言 6 个 job id：`job_scan_dm/job_zhihu_sync/job_trap_recheck/job_account_scan/job_evidence/job_case_publish` → ② 手动调用 `job_zhihu_sync()`（无 cookie 场景应安全空转）与 `job_scan_dm()`（无 pending 空转）→ ③ 观察 E1 全程日志无 scheduler 相关 ERROR。
【预期】6 job 注册（5 interval + 1 cron）；空转不抛异常不崩；全程无 ERROR。
【判定标准】job_snapshot 与预期集合一致；空转无异常；任一 job 抛未捕获异常 → P1。

- **P1（严重，记录并继续，交对应修复工程师）**：状态机非法迁移被放行；并发双写；幂等破坏；限流豁免失效；审计缺失；计数漂移；MCP 错误透传不一致。
- **P2（一般/观察项）**：封包不合规（裸 FastAPI 错误体）；无区分未冻结态；非标准头信任风险；体积告警；浏览器侧未实测项标注。
