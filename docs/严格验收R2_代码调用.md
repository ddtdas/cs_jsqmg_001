## 1. R1 修复逐项复核（t4 验收点）

### 1.1 ✅ job_trap_recheck await（R1 P0-1/P1-2）

- **落地**：scheduler.py:114-171 `job_trap_recheck` 重写 —— `engine.check_hit` 移入 `async def _run()` 并 `await`，外层 `asyncio.run(_run())`（与 job_scan_dm/job_zhihu_sync 同款模式）。
- **语义验证**：
  - `await engine.check_hit(conn, tid, text)` 真正执行协程；异常（退役/停用/非 active·monitored → TrapError）→ `break` 换下一个蜜饵，与旧注释意图一致；
  - 命中（`res["hit"]`）→ 立即 `GradingService().finalize(conn, detection_id=det_id, trap_hit_count=1)` → `_decide` 中 trap_hit → **L5**（grading.py:120）；随后补 `trap_hit_escalated` 事件 + commit；
  - **无 asyncio.run 阻塞风险**：check_hit 内部全为同步 DB/规则工作（无真实 IO await），事件循环即时完成；与既有 3 个用 asyncio.run 的 job 同构，无新增线程/循环问题；
  - **L5 自动路径闭环**：命中 → L5 → 告警（AlertService.evaluate，json_extract 幂等去重）→ 事件流 → job_evidence 的 L4/L5 证据包自动构建 → job_case_publish 的 L5 case_ready 门控恢复意义。链路完整。
- **新发现问题（P3-1）**：同一检测文本可被**多个**蜜饵命中，内层循环对每个 `res["hit"]` 都 finalize 一次 → 同一 det_id 出现多条 `detection_graded` + `trap_hit_escalated` 事件（告警有幂等去重不受影响，grade 重算幂等，仅事件重复+每次重跑 _auto_soc_analysis）。建议内层循环加"已升级跳过"去重（如先查该 det 是否已因 trap 命中升过 L5）。

### 1.2 ✅ L5 自动路径（含在 1.1 内）

- grading.py 未改动（R1 已含 `_auto_soc_analysis`）；本次由 scheduler 的 `finalize(trap_hit_count=1)` 触发 L3+ 自动社工分析 → `se_factors.soc_analysis` 回写 + `soc_lib_hit` 事件。链路验证通过。

### 1.3 ✅ evidence json_each 去重 + 409（R1 P1-3）

- **落地**：evidence.py:120-147 `build()` 在建包前对 `evidence_packages.det_ids` 做 `json_each` **精确**比对（`CAST(value AS TEXT)=?`，杜绝 LIKE `%1%` 误匹配 11/51），任一 det_id 已存在 → `409 evidence_exists`；scheduler job_evidence 预查同款 json_each 精确判重后跳过（R1 原 LIKE 误判/漏建修复）。
- **语义兼容**：
  - 手动/API/MCP 重复建包统一被服务层拦截（409）；
  - scheduler 自动路径先预查再 build，不会触碰 409（且 build 外层 try/except 兜底）；
  - api/evidence.py build 端点无改动即正确传播 409（utils.register_error_handlers 处理 ApiError.status_code）。
- **新发现问题（P2-1）**：`json_each(evidence_packages.det_ids)` 对**历史脏数据**无防护 —— 若某行 det_ids 为非 JSON 文本（手工改库/旧格式遗留），SQLite 报 `malformed JSON` → `build()` 直接 500；job_evidence 的 json_each 预查在 try/except **之外**（scheduler.py:228-236），同样 malformed → 整个 job 异常（@_safe 捕获记日志后任务中止）。R1 的 LIKE 方案对脏数据天然免疫。**建议**：查询加 `json_valid(det_ids)=1` 或外层 try/except 降级跳过该行；若预期库内只有程序写入的合法 JSON（det_ids 恒为 json.dumps 列表），优先级可降为 P3，但按本项目"防御式"风格应补。

### 1.4 ✅ cases publish 查重 + 409（R1 P1-4）

- **落地**：cases.py:65-79 在 `_PUBLISH_LOCK` 串行锁内先查 `SELECT id, redacted_payload FROM cases WHERE det_id=?`：
  - 同载荷（redacted_payload 相等）→ **幂等返回已存在案例**（不再重复触发 boost/distill —— 正确，避免在线学习/知识蒸馏连带重复）；
  - 异载荷 → `409 case_exists`；
  - 锁内先行查重 → 无 TOCTOU 竞态（单进程）；跨进程仍由 busy_timeout+重试兜底（注释明确）。
- **测试对齐**：test_r2_backend_fixes.py 并发 publish 用例更新为"恰 1×200 + 其余 409 case_exists（异载荷）+ 全库最终 1 条案例"断言，与服务实现一致；同载荷幂等路径有 200 返回保证既有调用方不崩。
- **新发现问题（P3-3）**：幂等返回路径忽略本次传入的 graph_tags/desensitize_log 差异（只要 redacted_payload 相同即返回旧案例）—— 语义上可接受，但若用户想"同载荷补标签"会被静默吞掉；建议 API 文档注明幂等判定维度。

### 1.5 ✅ 僵尸互斥（start.bat / start.ps1）

- **落地**：两个启动脚本在检测端口前先做 zombie 清理：遍历 `python.exe` 中 CommandLine 匹配 `app\.run` + `9200` 的进程，**杀掉除当前监听 PID 及其父进程外**的所有实例（父进程保护 = venv 重定向器，防止 R1 事故复盘中的"误杀健康 venv 重定向父进程"重演）；CIM 不可用时跳过不阻塞启动。
- **语义验证**：
  - `for /f "tokens=5"` 从 netstat LISTENING 行取 PID（IPv4/IPv6 行均 5 列）✓；
  - LPID 为空（master 未运行）时 `[int]''→0`，`$p=0, $pp=0` 分支均不误杀（实测 Windows PowerShell 5.1 语义 `[int]''`→0 无异常）✓；
  - `\\\"` 转义在 cmd→powershell 传递中存活（本地 cmd.exe 实测通过）✓。
- **新发现问题（P3-5）**：
  - 双实例竞态窗口收窄但未完全消除：A 实例刚 START_MASTER 尚未 netstat 可见前，B 实例 zombie 清理可能把 A 的新建进程当僵尸杀掉（毫秒级窗口；因 A 的监听 PID 尚未入表）。建议 START 后加 1-2s 保护窗口或再次 netstat 复核再清理；
  - start.bat 用 `-match '9200'` 匹配（过宽，可能误匹配含 9200 的其他命令行），start.ps1 用 `--port 9200`（精确）—— 建议 bat 同步改精确匹配，且再排除当前脚本自身 PID。
