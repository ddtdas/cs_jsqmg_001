## 1. 逐项修复

### 1.1 P0-1 / P1-1：job_trap_recheck 未 await（功能缺失，最高优先）

- 问题：`app/services/scheduler.py` `job_trap_recheck`（每 6h）对每条 scanned 文本调用
  `engine.check_hit(conn, tid, text)`，而 `TrapEngine.check_hit` 是 `async def`
  （trap_engine.py:459）。协程创建后从未 await/执行 → 函数体零执行，try/except/break
  全部失效，定时踩饵检测静默空转（不报错、不落地 hit/retired/事件）。
- 修复（scheduler.py，同文件 job_scan_dm 同款 asyncio.run 模式）：
  - 候选查询 `SELECT content` → `SELECT id, content`（命中后可定位触发检测）；
  - 双重循环体改 `async def _run()`，`await engine.check_hit(...)` 真正执行；
  - 外层 `import asyncio; asyncio.run(_run())`（与 job_scan_dm/job_zhihu_sync 一致）。
- 验证：tests/test_r6_r1fixes.py::test_job_trap_recheck_awaits_hit_and_escalates_l5
  （修复前此断言必失败：蜜饵不退役、检测不升级）/
  test_job_trap_recheck_no_hit_keeps_state（未命中状态不变、job 不抛）。

### 1.2 P1-2：蜜饵实锤命中 → 联动检测升级 L5（反诈核心闭环）

- 问题：`GradingService.finalize` 的 L5 条件（trap_hit>0）在所有自动调用点从不注入；
  `check_hit` 命中只退役蜜饵不改检测分级 → 线上 L5=0、case_ready=0、job_case_publish 永不产出。
- 修复：`job_trap_recheck` 命中分支内调用
  `GradingService().finalize(conn, detection_id=det_id, trap_hit_count=1)` —— 沿用既有
  单事务约定（UPDATE detections.grade=L5 + grade_reason 证据链含 trap_hit 信号 +
  detection_graded 事件 + AlertService.evaluate L3+ 告警 + post-commit 社工库自动分析），
  另追加 `trap_hit_escalated` 事件携带 {trap_id, detection_id} 关联审计；升级失败仅记日志
  不阻断后续蜜饵（防御式）。
- 效果：蜜饵实锤 → L5 → 告警 → job_case_publish 每日产出 case_ready → 人工 confirm 发布，
  "接入→分级→告警→案例"全链闭环。
- 验证：专项测试断言 grade=L5、grade_reason 含 trap_hit 信号、alerts 表 L5 告警、
  事件流含 trap_hit/trap_retired/trap_hit_escalated/detection_graded/alert_created。

### 1.3 P1-3：证据包去重 LIKE 误判 + 重复建包

- 问题：`job_evidence` 用 `det_ids LIKE '%{det_id}%'` 对 JSON 数组子串匹配——det 1 会被
  [11]/[51] 误判"已有包"而**漏建**；同时 evidence_packages 无唯一约束，实测 [150]×9、[1]×4 重复包。
- 修复：
  1. scheduler.py `job_evidence`：去重改为 json_each 精确判定（与 alerts 去重同款口径）：
     `SELECT 1 FROM evidence_packages WHERE EXISTS (SELECT 1 FROM json_each(evidence_packages.det_ids)
     WHERE CAST(json_each.value AS TEXT) = ?) LIMIT 1`，参数 str(det_id)。
  2. evidence.py `EvidenceService.build`：建包前对每个 det_id 做同样精确比对，任一已存在于
     既有包 → 409 `evidence_exists`（服务层去重约束，API/MCP/手动重复建包同样拦截）。
     顺序约定：先 `_detection_items` 严格校验（源缺失 → 404 detection_not_found，P2-C
     语义优先，test_r5 回归），再做重复建包检查（409 evidence_exists）。
- 验证：tests/test_r6_r1fixes.py::test_job_evidence_exact_dedup_avoids_like_collision
  （det 1 已有包时 det 11 不再被 LIKE '%1%' 漏建，且 det 1 不重复建包）、
  test_evidence_build_rejects_duplicate_det（重复 build → 409 evidence_exists）、
  test_r5_backend_fixes.py::test_evidence_verify_export_source_deleted_tolerant（顺序回归通过）。

### 1.4 P1-4：cases 发布去重（同一检测仅一个案例）

- 问题：cases 无 UNIQUE(det_id)、publish 不查重 → 同一检测可无限发案例（实测 det 345→1125 条、
  det 150→373 条），连锁放大在线学习 boost（顶到 10）/知识蒸馏/gate_logs 污染。
- 修复（cases.py `publish`，在 P1-D4 串行锁内、事务前查重）：
  - `SELECT id, redacted_payload FROM cases WHERE det_id=?`；
  - 已存在且**载荷一致** → 幂等返回已存在案例（不再重复 boost/distill）；
  - 已存在且**载荷不一致** → 409 `case_exists`（明确报错）。
- 说明：存量库已有重复数据（1695 条含大量重复），直接加 UNIQUE(det_id) 迁移会失败；
  本轮采用应用层去重（幂等 + 409），存量清洗与 UNIQUE 迁移列入 §4 P2-8（运维项）。
- 验证：tests/test_r6_r1fixes.py::test_case_publish_dedup_idempotent_and_conflict +
  test_r2_backend_fixes.py::test_concurrent_publish_no_500_no_false_404（断言更新：
  30 并发发布同一检测 → 恰 1×200 新建 + 29×409，无 500/404，最终仅 1 条案例）。

### 1.5 P1-5：双实例并存（运维/启动层）＋事故复盘

- 问题：同秒拉起两个 `python -m app.run --port 9200`（.venv 与系统 Python 各一），仅一个
  绑定 9200，另一个成僵尸实例持续刷 "no such table" 日志（实测 PID 7456 与 10040 并存，
  均创建于 12:54:46）。
- 关键事实（复盘所得）：Windows 上 `.venv\Scripts\python.exe` 是**重定向器进程**，它会
  spawn 真正的解释器（如系统 Python312）作为**子进程**来运行 `-m app.run`，子进程绑定端口。
  因此一个健康实例天然表现为"两个 app.run 进程"（重定向父 + 解释器子）——不能把未持端口的
  那个一律当僵尸。
- 修复（start.ps1 / start.bat，纯配置层）：
  - 僵尸判定 = 命令行含 `app.run` 且 `--port 9200` 且 **PID ≠ 监听 PID 且 ≠ 监听 PID 的父进程**
    （父进程即 venv 重定向器，受保护）；
  - 命中僵尸 → 告警 + Stop-Process -Force；CIM 不可用时跳过清理、绝不阻塞启动（防御式）；
  - start.bat 以 powershell 一行式实现同一逻辑（脚本保持纯 ASCII 编码安全）。
- 事故记录（诚实披露，接受验收复核）：
  1. 初次手动清理按旧判定（仅排除监听 PID）执行 `Stop-Process -Id 7456`，而 7456 恰是
     健康实例的 venv 重定向父进程 → 连带解释器子进程（原主控 10040）下线，9200 短暂不可用
     ——违反"不重启主控"约束（属事故性重启，非主动操作）；
  2. 第一次恢复用 SSH 会话内 `Start-Process` 启动 → 会话结束进程被杀（job object 回收），
     再次下线；
  3. 最终恢复：WMI `Win32_Process.Create` 分离式启动（venv python，`--host 0.0.0.0
     --port 9200`，与事故前一致）→ 跨 SSH 会话存活，health 200，数据无损；
  4. 已按"保护监听 PID 及其父进程"修正脚本逻辑，dry-run 实测健康实例两个进程
     zombie=False、0 僵尸（见 §2.5）。
- 验证：
  1. 本地 + 远程 PowerShell Parser 语法校验通过（start.ps1 PARSE OK）；
  2. 线上单实例实证：仅 venv 重定向器（12268）+ 解释器（5816 持 9200），health 200；
  3. dry-run 守卫对健康实例识别 0 僵尸。
