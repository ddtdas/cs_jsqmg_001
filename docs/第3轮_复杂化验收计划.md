## 类别 U：真实用户 / agent 工作流模拟（8 条）

### U1. 真实用户一天工作流串联（P0）
【操作】模拟真实用户一天（带思考停顿 3–8s、重复查看、翻页）：① 打开 `/ui/` 一键登录 → ② 看板页停留看统计/图谱 → ③ 信息收集页手动导入 3 条诈骗对话（不同骗术：杀猪盘/刷单/冒充客服）→ ④ 触发 inbox 批量扫描 → ⑤ 逐个打开检测详情（分级 explain）→ ⑥ 告警页标记 2 条已读 → ⑦ 证据页为 L3+ 检测建证据包 → 冻结 → 导出 → ⑧ 案例页脱敏发布 1 条 → ⑨ 会话历史页翻页浏览 → ⑩ 供应链页查一个嫌疑账号 → ⑪ 回到看板复查统计联动。
【预期】11 步全部真实浏览器可操作完成；统计（traps/detections/alerts/cases/graph）随步骤联动增长；无 500/白屏/卡死；每步停顿期间轮询（5s）不报错。
【判定标准】任一步骤操作失败/页面崩溃 → **P0**；统计联动缺项（如发布案例后图谱没涨）→ P1。

### U2. 真实 agent 批量工作流（含错误恢复）（P0）
【操作】模拟 agent（MCP stdio）：① `af_zhihu_import` 批量导入 10 条不同诈骗文本 → ② `af_scan_inbox` 批量消费 → ③ `af_build_evidence` 循环为前 5 条检测各建证据包 → ④ `af_publish_case` 批量发布 5 条（**其中第 3 条故意漏 confirm → 403** → agent 感知错误后**补 confirm+reason 重试成功**）→ ⑤ `af_freeze_evidence` 批量冻结 → ⑥ `af_export_evidence` 抽查 2 个。
【预期】①–⑥ 全部完成；第 3 条首次 403（错误码可见 `[confirm_required]`）、重试后成功；最终 5 案例入库、5 证据冻结、10 检测扫描完成。
【判定标准】错误恢复路径（403→重试）走通且错误码可见 → 通过；MCP 吞错成 200 或错误码不可见 → **P0**；批量中出现 500/连接中断 → P1。

### U3. 真实时间线：思考停顿 / 重复查看 / 翻页（P2）
【操作】U1 流程中以 3–8s 随机停顿执行；同一看板/同一检测详情**重复打开 3 次**；`/events`、`/cases` 各翻 3 页（page=1..3）。
【预期】重复查看不产生重复数据（除 scan 设计行为外）；翻页数据正确无串页；停顿期间无超时告警。
【判定标准】翻页串行/重复数据/超时（>5s）→ P2；无异常 → 通过。

### U4. 中途失败重试幂等（P1）
【操作】① 建证据包 build 中途"失败"：先 build 成功 pkg A → 再以相同 det_ids 重复 build → 应生成独立 pkg B（幂等语义：不覆盖 A）；② `af_publish_case` 同 det 第二次发布（第 1 轮 P2-B9 未实现，观察保留）→ 记录；③ scan/inbox 消费中途 kill 主控（在 X6 前做一次小验证：导入 3 条后 kill，重启后重跑 scan/inbox）→ pending 不丢失、processed 不重复。
【预期】① A/B 独立且 A 的哈希链不变；② 两次 200（记录观察）；③ 重启后 pending 仍在，重跑消费成功且每行只 processed 一次。
【判定标准】重试产生覆盖/数据丢失/重复消费 → **P1**；kill 重启丢 pending → P1。

### U5. 对话中断/恢复（P2）
【操作】U1 流程中段直接关闭浏览器标签 → 重新打开 `/ui/`（同浏览器进程）→ 会话是否保持；再完全关闭浏览器 → 重开 → 会话是否失效（sessionStorage 语义）。
【预期】同进程重开标签：会话保持（sessionStorage 存活）；完全关闭浏览器：需重新登录（第 1 轮 D5 已验证，回归抽查）。
【判定标准】关闭标签后同浏览器进程重开仍可进（保持）→ 通过；完全关闭后凭据仍有效（异常持久化）→ **P1**。

### U6. deep-link 直达各页（P1）
【操作】带有效会话直接打开：`/ui/dashboard`、`/ui/traps`、`/ui/scan`、`/ui/accounts`、`/ui/evidence`、`/ui/cases`、`/ui/events`、`/ui/alerts`、`/ui/zhihu`、`/ui/board`、`/ui/assets`、`/ui/risk`、`/ui/collection`、`/ui/supply-chain`、`/ui/sessions?tab=hit&id=<真实id>`、`/ui/sessions?tab=event&id=<真实id>`，共 16 个深链。
【预期】全部 200 渲染且各自加载真实数据；sessions 深链自动定位并打开详情抽屉。
【判定标准】任一深链 404/白屏/数据不加载 → **P1**；sessions 定位不到目标 → P1。

### U7. 浏览器刷新保持会话（P1）
【操作】登录后进入 dashboard → F5 刷新 ×3 → 数据仍加载、不跳登录；刷新瞬间 API 竞态（页面先发请求后拿 key？client.js 从 sessionStorage 同步读，无竞态——验证刷新不闪登录页）。
【预期】刷新后停留原页且数据正常；不出现登录页闪现/401 刷屏。
【判定标准】刷新后跳登录（会话丢失）→ **P1**；401 刷屏但最终恢复 → P2。

### U8. 多标签页会话隔离（P2）
【操作】同浏览器开 2 个标签都登录 → 标签 A 登出（清 sessionStorage）→ 标签 B 刷新 → 观察；新开标签页（Ctrl+T 手动输入 URL）→ 是否自动带会话（sessionStorage 不跨标签，预期需重新登录）。
【预期】A 登出不影响 B（sessionStorage 按标签隔离）；手动新开标签无会话 → 跳登录。
【判定标准】记录实际行为并核对设计语义（README 声称"会话级存储，关闭浏览器即失效"）；若 A 登出导致 B 也登出（异常全局共享）→ **P1**；行为与 README 不符 → P2（文档口径）。

## 类别 C：并发与压力（8 条）

### C1. 并发登录（P1）
【操作】20 线程同时 `POST /auth/local-login`（回环）→ 统计 200 数量与返回 key 一致性。
【预期】20/20 全 200，且全部返回**同一个**当前 key（读文件无写操作，天然一致）。
【判定标准】出现 500/连接失败 → P1；返回 key 不一致（读到轮换中间态）→ **P1**（与 A2 reset 竞态联动，若 C1 与 X6 之外无 reset 则应一致）。

### C2. 并发扫描吞吐与 429 语义（P1）
【操作】admin key（豁免限流）20 并发 × 5 批 = 100 次 `scan/text`（不同文本）→ 记录吞吐（req/s）、成功率、耗时 p95；随后无 key 20 并发同发（触发公共限流）。
【预期】admin 批 100/100 成功（无 429 无 500）；无 key 批按 60/min 桶语义 200/429 分布合理且**无 500**；吞吐记录（预期本机 >20 req/s）。
【判定标准】admin 批出现 500/异常 → **P1**（连接复用缺陷，第 2 轮 P1-11 复发检查）；无 key 批出现 500 → P1；吞吐 <5 req/s（异常退化）→ P2。

### C3. 并发蜜饵生成（P1）
【操作】30 并发 `POST /traps/generate-draft`（admin）→ 检查 honey_facts 增量 = 30、全部 draft 状态、无重复 fingerprint。
【预期】30/30 200；fingerprint 全部唯一；状态全 draft（HITL 不自动发布）。
【判定标准】增量 ≠ 30 / 重复 fingerprint / 非 draft → **P1**；500 → P1。

### C4. 并发案例发布一致性（P0，第 2 轮 P1-11 修复回归）
【操作】30 并发 `POST /cases/publish`（admin，confirm+reason 合规，30 条不同脱敏载荷、不同 det_id——预灌 30 条 L3+ 检测）→ 统计状态码分布；随后 `GET /cases` 核对 total 增量与 payload 一一对应。
【预期】30/30 200；无 `database is locked` 500；无 **误 404**（第 2 轮 D4 发现 `InterfaceError` 致已存在行误报不存在——重点复查）；cases 增量恰 30。
【判定标准】任一 500 → **P0**；误 404（存在却报不存在）→ **P0**；增量 ≠ 30（丢/重）→ P0；gate_logs 行数 = 30 → 通过。

### C5. 混合跑批：20–50 并发 × 10 分钟（P0）
【操作】模拟 10 分钟跑批：3 阶段各 3–4 分钟，每阶段 20–50 并发混合操作：阶段① 扫描+导入（scan/text、zhihu/import+scan/inbox 交替）；阶段② 蜜饵+证据（generate-draft、check-hit、evidence/build、freeze）；阶段③ 案例+查询（publish、GET cases/events/alerts/traps 混合）。期间**每 30s** 记录：错误率、吞吐、DB 文件大小、WAL 大小、进程 RSS；结束后 stats 对账（detections/traps/cases/alerts 增量与请求数一致）。
【预期】全程无进程崩溃/无连接重置；错误仅允许预期 429/409/404（且比例 <2%）；**不允许** 500/误 404/`database is locked` 堆栈（或出现即记录频次与场景）；DB 与 WAL 大小有界增长；统计对账一致。
【判定标准】崩溃/进程退出 → **P0**；500 或误 404 出现 → **P0**（并发写隔离缺陷，第 2 轮 P1-11 复发的实锤场景）；对账差异 >1% → P1；429 比例异常高（>50%）→ P1（写路径不该被公共限流影响，admin 已豁免则复查）。

### C6. EventsView 5s 轮询在并发下（P2）
【操作】浏览器保持看板/事件页打开（5s 轮询），同时跑 C5 阶段③ → 观察轮询请求（GET /events、/scan/hits、/traps?status=hit）在并发写期间的状态码与延迟。
【预期】轮询全部 200；延迟 <2s；UI 无卡死；轮询不触发 429（/events 非限流路径）。
【判定标准】轮询 500/延迟 >5s/UI 假死 → **P1**；429（意外被限流）→ P2；正常 → 通过。

### C7. 并发 check-hit / freeze 一致性回归（P0）
【操作】① 10 个并发线程对**同一 monitored 蜜饵** check-hit（同一命中文本）→ hit_count 与 retired 事件计数；② 10 个并发 freeze 同一未冻结 pkg → 200/409 分布；③ 10 个并发以相同 det_ids build → pkg 数。
【预期】① hit_count=1、`trap_retired` 事件=1、其余请求 409 `trap_retired`；② 恰 1 个 200、9 个 409 `already_frozen`；③ 10 个独立 pkg、哈希链各自正确。
【判定标准】① 双写（hit_count>1 或双退役事件）→ **P0**；② 双 200（重复冻结）或 500 → P1；③ pkg 相互污染 → P1。

### C8. 并发证据构建吞吐（P1）
【操作】20 并发 `evidence/build`（各 2 个 det_ids）→ 吞吐与成功率；随后全部 `GET /evidence/{id}` verify。
【预期】20/20 200；verify 全 intact=True；build+verify 总耗时 < 60s。
【判定标准】任一 build 500 → P1（写隔离复查）；verify 出现 intact=False → **P0**（哈希链错乱）。

## 类别 X：故障注入与恢复（8 条）

### X1. LLM 端点故障 → 熔断 → 恢复（P0）
【操作】① 起 mock LLM（`var/qa_round3/mock_llm.py`）→ 配置 `AF_LLM_BASE_URL/AF_LLM_API_KEY/AF_LLM_MODEL` 指向它 → 重启主控 → health 应 `llm=configured`；② mock 切"500 模式" → 连续 `scan/text`（触发 LLM 复核的话术）→ 观察第 1–3 次调用失败计数 → 第 4 次起应**直接熔断降级**（不发网络，响应仍 200 纯规则判定）；③ 日志出现熔断记录；④ mock 切回"正常模式" → 再 `scan/text` → **观察能否自动恢复**（按 llm_provider.py:233 `if self.degraded: raise`——当前实现预期**无自动恢复**，熔断状态持续到进程重启）。
【预期】② 熔断生效（规则降级不瘫）；④ 预期 **P1 发现**：熔断后无半开/定时恢复机制，LLM 恢复后仍需重启进程才能复用（确认代码无 recovery 路径）。
【判定标准】熔断不生效（一直打网络/响应 500）→ **P0**；熔断后服务不瘫（纯规则 200）→ 通过；LLM 恢复后**自动**恢复（存在恢复机制）→ 通过；不能自动恢复 → **P1**（建议：熔断加时间窗半开探测或 reset 端点，交 backend-core）。

### X2. LLM 恢复后降级链与 health 行为（P1）
【操作】承接 X1：熔断状态下 ① `GET /system/health` 的 llm 灯（预期仍显示 configured——health 读配置不读熔断态，记录口径）；② 熔断期间 `scan/text` 响应字段 `llm_used=false`（降级证据）；③ 重启主控后（清熔断）mock 正常 → `llm_used=true` 恢复；④ `GET /config` 的 llm 段落与预算字段。
【预期】①②③ 与实现一致；health 灯与熔断态脱钩属口径问题（记录，若文档宣称 health 反映熔断 → P2 文档漂移）。
【判定标准】降级链断裂（熔断期间 scan 500）→ **P0**；恢复后 llm_used 仍 false（不恢复）→ P1；health 口径与文档不符 → P2。

### X3. 知乎通道故障降级（P1）
【操作】① 无 cookie 时 `GET /zhihu/channels`（四通道健康结构与 degraded 标记——ch-a/ch-b 预期 ok=false + 原因）→ ② `POST /zhihu/channels/ch_a/login` 注入垃圾 cookie → 预期 422 `invalid_cookie`（不代登录、不裸存）→ ③ 注入合法结构 cookie（用测试 Fernet 直接写库造一个加密 cookie）→ `POST /zhihu/channels/ch_a/verify` → 结构校验结果；④ `GET /zhihu/status`（限速水位/退避冷却/会话——不含明文 cookie）；⑤ 调度器 `job_zhihu_sync` 无 cookie → 安全 no-op（日志 INFO）。
【预期】①/④/⑤ 正常；② 422；③ 记录（真实登录态由实际抓取探明，环境无网络则记录"结构通过/登录态未验证"）。
【判定标准】任一接口 500 → P1；channels 返回泄漏 cookie 明文 → **P0**；降级链（CH-A→CH-B→CH-D 提示）在注释/响应 note 中体现 → 通过。

### X4. 知乎限流超配额 → 退避冷却 → 恢复（P1）
【操作】venv 脚本直连桥接（真实主控进程内）：`AF_ZHIHU_RATE_LIMIT=3` 重启主控 → 连续调用 `bridge.fetch_inbox`（无 cookie 场景会快速走到限速/不可用路径）或直接调 `bridge._gate('ch-b')` 25 次 → 统计 RateLimitExceeded 次数；`GET /zhihu/status` 观察限速水位归零与退避冷却；等退避窗口后再次调用 → 恢复（冷却到期）。
【预期】全局令牌桶容量 3 → 第 4 次起 RateLimitExceeded；status 水位反映；退避冷却期间持续拒绝；到期后恢复可用。
【判定标准】限流不生效（25 次全过）→ **P1**（全局单例失效，第 2 轮修复回归）；冷却永不恢复 → P1；status 水位与实测不符 → P2。

### X5. 数据库锁 / 只读故障注入 → 恢复（P0）
【操作】① **写锁注入**：第二进程对 `af.db` 执行 `BEGIN EXCLUSIVE` 持锁 → 主控发 `scan/text`/`evidence/build` 等写操作 → 预期 busy_timeout 5s 后 500 封包（`database is locked` 类错误落日志）→ 释放锁 → 再发同请求 → 恢复 200；② **只读注入**：`attrib +R af.db`（Windows 只读属性）→ 写操作 500、读操作 200 → `attrib -R` → 恢复；③ 全程主控进程存活、health 200（health 只 SELECT 1）；④ 恢复后数据完整性 `PRAGMA integrity_check` = ok。
【预期】故障期：写 500 封包（不崩、不吞）、读 200、health 200；恢复后写立即 200；DB 无损。
【判定标准】故障期主控崩溃/进程退出 → **P0**；写操作静默成功（假装写入实未落库）→ **P0**；恢复后 integrity_check 非 ok → **P0**；500 封包不含内部堆栈路径（第 2 轮 E3 修复回归）→ 通过。

### X6. 主控被杀 → WAL 恢复 → 重启（P0）
【操作】① 导入 5 条 pending + 触发部分写（build 2 个 pkg、freeze 1 个）→ **立即 `taskkill /F`（不等响应完成，模拟崩溃）** → ② `netstat` 确认 9200 释放 → ③ `start.bat` 重启 → health 200 → ④ 验证：`PRAGMA integrity_check`=ok；pending 检测仍在（未丢）；已提交的 pkg/freeze 状态正确（frozen=1 那条保持）；WAL 被正确恢复（无 -wal 残留异常）→ ⑤ `GET /events` 可查、调度器 job 重新注册（job_snapshot 6 条）。
【预期】重启后数据零丢失（已提交事务）、未提交事务被 WAL 回滚（不出现半写状态）；服务完全恢复。
【判定标准】重启后 integrity_check 非 ok / 已提交数据丢失 / 出现半写行（如 frozen=1 但无 events）→ **P0**；恢复后功能全可用 → 通过；首启健康探测 20s 内通过（start.bat 语义）→ 通过。

### X7. stop/start 循环与 UI 恢复（P1）
【操作】① `stop.bat` → 9200 释放、二次 stop 提示未运行（幂等）；② `start.bat` → 新进程 + health + 浏览器打开 /ui/；③ 重复 stop/start ×3 循环；④ 每次循环后浏览器刷新 /ui/ → 登录 → 看板数据正常。
【预期】3 次循环全部成功；PID 每次变化；无端口占用冲突；UI 每次都可用。
【判定标准】任一循环失败（端口未释放/health 不过/UI 不可用）→ **P1**；stop 后进程残留（taskkill /T 未杀干净）→ P1。

### X8. 调度器 job 异常注入不崩（P1）
【操作】venv 脚本（主控进程内注入）：① 手动调用 6 个 job 函数各 1 次（正常空转）；② **异常注入**：临时把 `job_scan_dm` 依赖的 speech_engine 打桩成抛异常（monkeypatch）或制造异常数据（如 detections 行 content=NULL 触发 analyze 异常）→ 调 job → 观察 `_safe` 装饰器捕获（日志 `job job_scan_dm failed: ...`）→ 调度器不崩、其它 job 仍可运行；③ 查 `job_snapshot()` 6 job 仍在、`get_jobs()` 无 removed；④ 下一轮正常数据再跑 job → 恢复。
【预期】job 抛错仅落日志（`canary.scheduler` ERROR），调度器线程存活；其它 job 不受影响；下次正常执行成功。
【判定标准】job 异常导致调度器整体退出/进程崩 → **P0**；异常后该 job 永久失效（不恢复）→ P1；仅日志记录且恢复 → 通过。

## 类别 L：长时间运行稳定性（4 条，全程后台采样）

### L1. 30 分钟长稳监控（P1）
【操作】从 U 阶段结束起后台采样脚本每 10s 记录：进程 RSS（MB）、`var/logs/app.log` 行数、`af.db` 与 `af.db-wal` 大小（KB）、health 状态、最近 60s 错误数（日志 ERROR 计数）；持续 ≥30 分钟（覆盖 C/S/D 阶段），X6 强杀前结束采样。
【预期】RSS 无持续单调增长（允许小幅波动 <20%）；日志行数平稳增长（无突发刷屏）；WAL 大小有界（checkpoint 生效）；health 全程 200；无新增堆栈。
【判定标准】RSS 单调增长 >50% 且不回落 → **P1（内存泄漏）**；WAL 无界增长（>100MB）→ P1；ERROR 突发（>10 条/分钟且非注入场景）→ P1。

### L2. 调度器周期执行日志（P2）
【操作】30 分钟窗口内核对：`job_zhihu_sync`（5min 间隔 → 预期 ≥5 次执行日志/安全 no-op）、`job_scan_dm`（10min → ≥2 次）、`job_trap_recheck`（6h → 0 次，符合周期）、`job_case_publish`（每日 3:00 → 0 次）；`job_snapshot()` 抽查 next_run 合理性。
【预期】周期执行次数与间隔定义一致；空转 job 日志为 INFO 非 ERROR。
【判定标准】job 该跑没跑（日志缺失）→ P2；job 执行抛 ERROR → P1（并入 X8 判定）。

### L3. WAL checkpoint 有界（P2）
【操作】L1 采样中重点看 `af.db-wal` 峰值；C5 跑批后立即查 WAL 大小并手动 `PRAGMA wal_checkpoint(PASSIVE)`（或等自动 checkpoint）。
【预期】WAL 峰值 < 自动 checkpoint 阈值（1000 页 ≈ 4MB 内）或恢复后回落；跑批后 WAL 不无限增长。
【判定标准】WAL 持续增长不回落且 >50MB → **P1**；正常 → 通过（P2 级别观察）。

### L4. 长稳后健康与计数自洽（P2）
【操作】L1 结束（X6 前）取 `GET /system/stats` + `PRAGMA integrity_check` + `GET /events` 分页抽查。
【预期】stats 计数与 C5 对账一致（或已由 C5 记录）；integrity_check=ok；events 分页无空洞。
【判定标准】integrity_check 非 ok → **P0**（联动 X6）；计数对账偏差 → P1（联动 C5）。

### S1. 预灌 100+ 检测 / 50+ 蜜饵 / 20+ 案例（P0 准备 + P1 断言）

【预期】分页无重复无缺漏；过滤计数自洽。
【判定标准】翻页重复/缺行 → **P1**；tag 过滤总数与预灌标签数不符 → P1。

### S3. UI 与 API 响应时间（P2）
【操作】大库下测量（httpx 计时，每端点 10 次取 p95）：`/cases`、`/events`、`/traps`、`/alerts`、`/scan/hits`、`/cases/graph`、`/system/stats`、`/accounts/{url_name}`、`/grading/explain/{id}`；浏览器侧记录 dashboard 首屏时间。
【预期】本地 p95 < 1.5s；无端点出现秒级退化（>5s）；graph/stats 聚合查询在 100+ 行量级不退化。
【判定标准】任一 p95 > 5s → **P1**（大库性能退化）；>1.5s 但 <5s → P2 记录。

### S4. 会话历史页性能（P2）
【操作】浏览器打开 `/ui/sessions`（聚合 scan/hits 6 + events 6 + traps?status=hit 6 + 详情抽屉）→ 记录加载耗时与轮询稳定性；切换 tab（hit/event/trap/alert）各一次。
【预期】首屏 <2s；tab 切换 <1s；轮询 5s 不卡顿。
【判定标准】首屏 >5s / tab 切换卡死 → **P1**；>2s 记录 P2。

### S5. 供应链页与图谱性能（P2）
【操作】`/ui/supply-chain` 页（accounts/check + timeline）与 `/ui/board` 图谱（cases/graph + echarts）在大库下实测；`GET /accounts/{id}/timeline` 对预灌嫌疑账号（含踩饵记录）响应时间。
【预期】页面加载 <3s；timeline <1s；ECharts 渲染不白屏。
【判定标准】白屏/超 5s → P1；正常 → 通过（P2 记录实测值）。

## 类别 D：可用性细节（6 条）

### D1. 主控未启动时的 UI 行为与引导（P1）
【操作】① `stop.bat` 停主控 → 浏览器访问 `/ui/` → 记录（预期连接拒绝——UI 由主控托管，属预期，重点是**不假死不无限转圈**）；② 重新启动后访问恢复；③ 主控运行但 DB 被锁（X5 场景）时 UI 各页的报错呈现（预期友好错误提示而非白屏/原始堆栈）。
【预期】① 浏览器显示连接失败页（Chrome 原生），README/快速开始有"先 start.bat"引导；③ UI 错误处理显示友好文案（第 1 轮 A10 修复后无原始 pydantic 文本——回归）。
【判定标准】③ 出现原始堆栈/白屏 → **P1**；① 行为与引导文档不符 → P2。

### D2. 断网/重连自动恢复（P1）
【操作】浏览器停留看板（5s 轮询）→ `stop.bat` 停主控（模拟断网）→ 观察 UI（轮询失败错误提示，不崩）→ `start.bat` 重启 → 观察下一轮轮询自动恢复（数据重新加载，无需手动刷新）。
【预期】断连期 UI 有错误态提示且页面不假死；重连后 5s 内自动恢复数据。
【判定标准】重连后不自动恢复（需手动刷新）→ **P1**；断连期页面假死/无限 loading → P1。

### D3. 多端会话与 key 一致性（P1）
【操作】同一 key 同时：浏览器（sessionStorage）+ MCP env + curl 三端并发使用 10 分钟（融入 C5）→ 三端数据视图一致（同一 stats）；任一端触发 401（如 X6 重启后 key 不变则无 401——设计上 key 文件不变，验证重启后**同一 key 继续有效**，除非 reset）。
【预期】三端共享同一数据视图；**重启（非 reset）不轮换 key**——`data/bootstrap_admin_key.txt` 不变 → 浏览器/MCP/curl 无需重配。
【判定标准】重启后 key 变化（未 reset 却轮换）→ **P1**；三端视图不一致 → P2。

### D4. 刷新/导航保持会话与参数（P1）
【操作】在 `/ui/sessions?tab=alert&id=<真实告警id>` 深链页刷新 → 仍定位到该告警详情；在 `/ui/events` 第 3 页刷新 → 停留第 3 页（或记录回到第 1 页的口径）。
【预期】深链刷新保持定位；分页刷新行为与实现一致（记录）。
【判定标准】深链刷新丢失定位 → P1；分页刷新跳回首页 → P2（记录口径）。

### D5. 多标签页并发轮询互扰（P2）
【操作】同浏览器 3 个标签同时开看板/事件/告警页（共 15s 间隔 3 个轮询循环）→ 观察请求错峰、无 429、无数据串台（tab 间 Vue 实例隔离）。
【预期】3 个轮询循环正常；数据互不串台；无 429（/events 等非限流）。
【判定标准】数据串台（A 标签显示 B 标签数据）→ **P1**；429/卡顿 → P2。

### D6. 多用户共用一库的提示（P2）
【操作】README / docs/00-项目概述 检索：是否声明"本机单用户工具；多人共用同一数据库时无数据隔离，共享全部数据与 key"。
【预期】文档含单用户定位与共用风险提示（README §1"不是面向公众的多用户 SaaS"+ 合规声明）。
【判定标准】无任何共用/隔离声明 → P2（建议 README 补一句）；已有 → 通过。

## 缺陷分级规则

- **P0（阻断）**：进程崩溃/退出；并发写 500 或误 404（第 2 轮 P1-11 复发）；强杀重启后数据丢失/半写；DB 锁故障期静默假写入；MCP 吞错；哈希链错乱。

3. **X1 熔断恢复预期**：按 llm_provider.py:233 当前实现，熔断后无自动恢复是**预期发现项**（P1 建议），不是执行错误；恢复验证用"重启主控"作为对照基线。
4. **C5 跑批期间**：admin key 豁免公共限流（X 类中若涉及无 key 请单独窗口）；429 只允许出现在无 key 场景。
5. **X5 锁库**：`BEGIN EXCLUSIVE` 持锁期间主控写操作会阻塞最多 5s（busy_timeout）后 500——**等 5s 再断言**，勿提前判 500。
6. **L1 采样与 X6 互斥**：采样进程必须在 X6（强杀主控）前停止，否则采样数据含 kill 噪声；X6 后如需长稳数据，另起一轮 10 分钟迷你采样。
7. **key 一致性**：重启（非 reset）不轮换 key；若 X 类中触发 reset（不建议），全队同步换 key。
8. 报缺陷必须附：操作序列/并发数/耗时曲线/DB 对账 diff/复现脚本——与前两轮同一纪律。
