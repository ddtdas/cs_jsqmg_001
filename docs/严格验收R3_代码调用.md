## 1. R2 修复逐项复核

### 1.1 ✅ 升级路径补偿原子化（trap_hit_escalation_pending 重放）—— 逻辑正确，遗留清理缺口

- **落地**（scheduler.py:114-180, 183-257）：新增三个函数 `_det_already_trap_escalated` / `_escalate_detection` / `_escalate_pending`，job_trap_recheck 开头先 `_escalate_pending(conn)` 重放未决升级，再走蜜饵复查。
- **正确性验证**：
  - **幂等**：`_escalate_detection` 先查 `_det_already_trap_escalated`（grade=L5 且 grade_reason 含 trap_hit 信号）→ 已升级返回 False 跳过；未升级才 finalize(trap_hit_count=1)→L5；杜绝多蜜饵命中同检测的重复事件/重复社工分析；
  - **恢复路径**：job 实时升级失败 → 写 `trap_hit_escalation_pending` 事件 + commit（不再静默丢失）；下一轮 job 重放 → `recovered=True` 标记的 `trap_hit_escalated` 事件；仍失败仅记日志留待下轮；
  - **失败留待**：`_escalate_pending` 内异常 continue 不中断其余 pending；坏 JSON/非法 det 跳过；
  - **测试覆盖**：test_r7_r2fixes.py `test_trap_recheck_pending_compensation`（无蜜饵仅重放→L5+recovered 事件+第二轮幂等不再新增）、`test_trap_recheck_multi_trap_hit_single_escalation`（双蜜饵→仅 1 次升级+双退役）均断言正确。
- **P2-1 新发现**：`_escalate_pending` 在 `upgraded=True` 后**只计数、不删除/不标记 pending 事件行**（无 DELETE/UPDATE）。影响：
  1. 已重放成功的 pending 行永久保留在 events 表，每轮 job 重扫（无效 IO）；
  2. events 表随失败事故次数无界增长；
  3. 若 det 后续被删（已退役蜜饵场景），`_escalate_detection` 抛 detection_not_found → 每轮重试永不收敛（"留待下轮"退化为"永远重试"）；
  4. 运维审计时无法区分"已恢复"与"仍挂起"（recovered 标记只写在成功事件里，pending 原行不变）。
  **修复建议**：重放成功后 DELETE 该 pending 事件行（或 UPDATE payload 追加 `resolved_at`/`status:'recovered'`）；若 det 不存在（404）也应标记终态（如 payload 追加 `terminal_error` + 停止重试）。
