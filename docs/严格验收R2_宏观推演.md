## 3. 事故复盘："僵尸实例"真相（R1 结论修正）

R1 我报告"双实例并存（7456+10040 同 cmdline，仅 10040 持端口）"。**R2 查证后机制判断有误，需正式修正：**

1. **真实架构**：`.venv\Scripts\python.exe` 是 **venv 重定向器**（Windows venv 标准行为）——它启动基座解释器 `Python312\python.exe` 作为**子进程**并等待；**子进程**持有 9200。两者 cmdline 相同（都显示 `-m app.run --port 9200`）。**7456+10040 是同一逻辑实例的父子对，不是两个实例**。start.bat/start.ps1 注释与 R2 进程树（12268 父 → 5816 子持端口）双重印证。
2. **"no such table" 错误来源**：app.log.1/app.log 中的批量错误（12:44:29、12:48、12:58…）出现在"调度器已启动/已停止"快速连发序列（15:43:00–15:43:15 秒级 20+ 次启停）附近 = **pytest 生命周期测试**（TestClient lifespan 反复启停 + 临时空库建表前 job 首火）写入共享日志。非生产实例噪声。
3. **R1 事故（误杀）复盘**：互斥清理最初只保护监听 PID，把健康的 venv 重定向父进程当作僵尸 Kill → 子进程（真实服务）连带终止 → 主控下线。R2 修复：safePids 纳入监听者的父进程，清理逻辑正确。
4. **R1 P1-5 修正后结论**：同秒双启动竞态**是真实风险**（两个 launcher 并发 start 会各自拉起一对进程，仅一对能绑定端口，另一对残留并可能跑调度器/双写），互斥清理保留必要 ✅；但"当前线上双实例"的定性不成立——现网为单逻辑实例（12268→5816）。

## 4. 并发 / 时序推演（修复后 9 job + 新写路径）

- **job_trap_recheck ↔ job_scan_dm**：操作状态集不相交（scanned vs pending）✅ 无重叠。
- **job_trap_recheck 内部升级路径（新写路径）**：三次提交（check_hit 的 trap 状态 / finalize 的检测+告警 / trap_hit_escalated 事件）。**任一后续提交失败 → 蜜饵已退役、检测未升级，且蜜饵退役后下次 job 不再复查该饵 → 实锤升级永久丢失**（仅 log.warning）。→ **P1-A**。建议：升级段与 check_hit 合并为单事务（check_hit 命中与升级同 commit），或失败时按 text_hash 反查检测补偿升级。
- **多蜜饵命中同一检测**：候选文本同时匹配 trap A、B → 两次 finalize（grade 幂等 L5、alert 幂等去重 ✅），但产生 2 条 detection_graded/trap_hit_escalated 事件、2 次 soc 分析。P2。
- **手工 check-hit API ↔ job**：良性竞争（一方先退役，另一方 409 trap_retired → break）。但**手工路径命中不升级检测**（api/traps.py 只返回结果）→ 与 job 行为不一致（P1-C）。
- **job_evidence ↔ manual build**：check-then-insert 竞态残余窗口（双层 json_each 检查均在 insert 前，无行锁；job 12h 一次 + 手工偶发 → 概率极低）。P2。
- **job_case_publish ↔ 手工 publish**：job 只产 case_ready 事件不写 cases；手工 publish 落 cases；次日 job 经 NOT EXISTS 跳过 ✅ 无重复。
- **L5 升级 ↔ job_evidence**：升级先行（≤12h 内建包），包内含最终 se_factors（含 soc_analysis）✅。
- **persona_sim ↔ publish_now**：R1 遗留竞态（SELECT→UPDATE 无行锁）未修，仍在（published=total 后不再触发，实际窗口小）。P2。
- **knowledge import 并发 UNIQUE 竞态**：R1 遗留未修（IntegrityError 未捕获）。P2。

## 6. 剩余 Top 风险清单（R2）

### P1
- **P1-A｜trap 升级路径非原子（修复引入）**：check_hit 与 finalize 分两次提交，finalize 异常 → 蜜饵已退役不可重试 + 检测未升级；事件流有 trap_hit 但无 detection_graded/告警 → 静默不一致。修复：升级并入 check_hit 事务，或失败补偿（按 trap_hit 事件反查补偿升级）。
- **P1-B｜存量重复数据无清洗**：cases 重复（det 345×1125、150×373、3067×2 等）+ evidence 重复包（[150]×9、[1]×4、[130,128]×2 等 9 组）仍在；实证 pattern 权重未被污染（pattern.boost=0，61 词条全 seed 源、权重分布 5-10 正常），影响限于案例列表/图谱聚合失真 + 审计噪音。建议：一次性幂等清洗脚本（保留每组第一条 + gate_logs 审计）。
- **P1-C｜手工 check-hit 不升级检测**：POST /traps/{id}/check-hit 命中仅退役蜜饵，不联动 detection.grade/告警/案例 → 与 job 行为不一致，手工触发实锤仍不进案例管道。建议：命中后反查最近 scanned 匹配检测并升级，或至少在文档/响应中明示该限制。

### P2
- cases 409 后无更新/删除 API（错误发布无法修正）；evidence 无追加截图/补充材料机制
- 多蜜饵命中同一检测 → 重复升级事件/重复 soc 分析（幂等但噪音）
- knowledge import 并发 UNIQUE 竞态 500（R1 遗留）；persona publish_due/publish_now 竞态（R1 遗留）
- scanned 滞留无归档（634 条>1 天）；告警 1448 unread 无自动已读/降噪；events/gate_logs 只增无归档策略
- IOC 提取噪声（QQ 正则命中银行卡子串，R1 遗留，实测 knowledge iocs 含虚假 qq）
- LLM 慢时 job_scan_dm 单轮 20-50min 背压（R1 遗留，有界增长）
- 启动互斥残余：仅 start.bat/start.ps1 路径生效，直接 `python -m app.run` 绕过；PID 复用理论误杀（极低概率）
