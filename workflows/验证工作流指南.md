# 金丝雀蜜罐 · 验证工作流指南

> 可复用：任何一轮「全面验证 + 双盲交叉 + 修复闭环」都按本指南执行。
> 模板脚本：`workflows/canary-full-verify.template.js`；设计依据：`PLAN-其它方向深度验证与对标升级.md`。

---

## 一、工作流总览（五阶段）

```
阶段1  六方向并行验证   →  安全纵深 / 性能并发 / 数据完整性 / MCP+WebUI / 供应链采集 / 内嵌DSH
阶段2  双盲交叉抽查     →  独立一队（不读源码不互通）从最终行为抽查每方向 2-3 项
阶段3  修复闭环         →  汇总 P0/P1/P2 → 修复子代理（按优先级批量）→ 专项验证
阶段4  全量回归         →  pytest 全量 + 前端构建 + 主控重启（加载修复）+ 清理双进程
阶段5  浏览器人类验收   →  关键修复项 UI 实测 + 综合报告落盘
```

## 二、执行前准备（必做）

1. **主控基线**：`GET /api/v1/system/health` 200；`pytest -q` 记录基数
2. **admin key**：读 `data/bootstrap_admin_key.txt`（勿硬编码——测试会触发 reset-key 轮换）
3. **端口清点**：3080（全局）/3090（找点事干）/3091（无关 agl-ctl）/3092（内嵌 DSH）/9200（主控）——测试期勿动 3080 与 3092
4. **环境干净**：确认 9200 单进程（`netstat -ano | findstr :9200`），多进程需先清理
5. **通知各队**：admin key 可能被 reset-key 轮换、主控可能被重启——每队跑前重读 key、避免并发 reset

## 四、阶段2：双盲交叉

- 独立一队**黑盒**验证（仅 API，不读源码不互通），每方向抽 2-3 项
- 输出与阶段1 各队结论**交叉比对**：一致→确认；不一致→证据复核
- 重点交叉点：鉴权矩阵 / 漏检话术 / 数据完整性 / MCP 透传 / 内嵌 DSH 隔离

## 五、阶段3：修复闭环

1. 汇总 P0/P1/P2 → 按「安全 > 数据 > 功能 > 体验」排优先级
2. 每批修复 = 一个 workflow agent（含：文件:行改动 + 专项验证 + 新增回归测试 + 不改既有用例语义）
3. 修复原则：最小改动、保持统一封包、幂等迁移、D5 降级不破坏
4. 修复后立即：`pytest -q` 全量 + 专项验证证据

## 九、常见坑（本阶段经验）

1. **PowerShell 中文编码**：请求体必须 `[Text.Encoding]::UTF8.GetBytes()` 字节 POST，字符串方式中文会乱码导致漏检误判
2. **admin key 轮换**：测试会 reset-key，全队统一"读文件现值"，禁止硬编码
3. **9200 多进程**：SSH 会话启动的进程可能残留，用 `netstat` 确认单监听
4. **内嵌 DSH**：启停用 `dsh/start.bat`（WMI 常驻），勿手动 kill；ps1 重定向需 UTF-8
5. **只读验证**：验证队不改产品代码；发现缺陷交修复队
